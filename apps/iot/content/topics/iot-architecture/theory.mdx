## Idea

Diseñar TI tradicional es como diseñar una casa: pocos usuarios, ambiente controlado,
fácil de asegurar. Diseñar IoT es como diseñar un estadio masivo: miles a millones de
endpoints, dispositivos muy diversos, mucha más escala y exposición. IoT no es "más
dispositivos de TI": cambia el problema arquitectónico completo. Por eso el curso usa
modelos de referencia (oneM2M, IoTWF) para ordenar dónde vive cada pieza —sensor,
gateway, protocolo, analítica— dentro de un sistema IoT.

## Conceptos

### TI tradicional vs. IoT: "todo es sobre los datos"

| | TI tradicional | IoT |
|---|---|---|
| Analogía | Diseñar una casa | Diseñar un estadio masivo |
| Usuarios/dispositivos | Limitados, ambiente controlado | Miles → millones de endpoints |
| Soporta | Aplicaciones de negocio (correo, web, CRM, BD) | Datos generados por sensores |
| Foco | Servicio confiable y continuo | Transportar → recolectar → analizar → actuar |

> La idea central de IoT es mover datos del mundo físico hacia una acción con sentido.

### Los cuatro impulsores (drivers) de la arquitectura IoT

1. **Escala masiva**: de miles a millones de endpoints; se necesita direccionamiento
   escalable (IPv6).
2. **Seguridad**: dispositivos expuestos y físicamente accesibles → superficie de
   ataque más grande y amenazas nuevas.
3. **Restricciones (constraints)**: dispositivos limitados + redes no confiables → poca
   energía, memoria, ancho de banda y procesamiento.
4. **Legado y tiempo real**: sistemas antiguos conviven con decisiones inmediatas →
   se necesitan gateways, edge computing y analítica en tiempo real.

### Iniciativa IoTWF (Cisco, IBM, Rockwell Automation, 2014)

El **IoT World Forum (IoTWF)** propone **7 capas**: las 3 primeras son la parte OT
(*Operational Technology* — lo físico/tiempo real) y las 4 restantes son la parte IT
(perspectiva comercial de los proveedores, interesante para interoperabilidad y

### Capa 1 — Things: sensores y actuadores

Antes de elegir una tecnología de red hay que entender las características del
dispositivo ("thing"), porque **el "thing" determina los requisitos de red**:

| Característica | Opción A | Opción B |
|---|---|---|
| Energía | A batería → limitado en energía | Conectado a la red eléctrica → menos restricciones |
| Movilidad | Estático (ubicación fija) | Móvil (cambia de ubicación) |
| Frecuencia de reporte | Baja: una vez al mes | Alta: cada pocos milisegundos |
| Tipo de dato | Simple: binario / on-off | Rico: telemetría / multidimensional / video |

### Capa 2 — La red de comunicaciones

Conecta las "cosas" con las aplicaciones, en cuatro partes:

1. **Red de acceso**: la "última milla" que conecta a las cosas. Topologías estrella,
   malla o punto a punto. Ejemplos: Wi-SUN, LoRaWAN, IEEE 802.11ah.
2. **Gateways y backhaul**: el gateway conecta los dispositivos locales con la red
   central; el backhaul transporta esos datos a mayor distancia.
3. **Transporte de red**: IP da conectividad de capa de red; UDP habilita un
   transporte liviano.
4. **Gestión de red**: protocolos pensados para comunicación IoT eficiente — **CoAP**
   (basado en UDP) frente a **MQTT** (basado en TCP).

### Capa 3 — Aplicaciones y analítica

Convierte datos en valor, con tres tipos de aplicación:

- **Analíticas**: combinan datos de varias cosas, visualizan estados/tendencias,
  generan reportes históricos, identifican patrones y anomalías.
- **De control**: convierten información en acciones automatizadas, modificando el
  comportamiento de dispositivos físicos.
- **Analítica de red**: monitorea la salud y desempeño de la red IoT, detecta fallas
  y comportamiento anormal, ayuda a prevenir accidentes operativos.

## Método paso a paso

Para ubicar un componente dado dentro del modelo IoTWF:

1. Pregunta si el componente **genera o consume** el dato físico (sensor/actuador) →
   capa 1.
2. Si sólo **transporta** el dato (radio, gateway, protocolo de red) → capa 2; dentro
   de ella, distingue si es la "última milla" (acceso), el puente (gateway/backhaul),
   el transporte (IP/UDP) o la gestión (CoAP/MQTT).
3. Si **procesa, visualiza o decide** con el dato ya recolectado → capa 3.
4. Verifica con los 4 impulsores (escala, seguridad, restricciones, legado/tiempo
   real): ¿por qué esa capa es la que mejor atiende ese impulsor para este caso?

## Ejemplo resuelto

*(derivado)* Un sensor de humedad de suelo a batería que reporta una vez al día por
LoRaWAN a un gateway, que reenvía por MQTT a un dashboard en la nube que genera
alertas de riego.

- Sensor de humedad → **capa 1** (a batería, estático, baja frecuencia de reporte,
  dato simple).
- LoRaWAN (red de acceso) + gateway → **capa 2**, parte "red de acceso" y "gateway y
  backhaul".
- MQTT (TCP) → **capa 2**, parte "gestión de red".
- Dashboard que genera alertas → **capa 3**, aplicación de control (decide accionar
  el riego) y analítica (visualiza tendencias de humedad).

## Errores típicos

- Confundir "capa de conectividad" con "el protocolo de aplicación": la capa 2 cubre
  desde la radio hasta CoAP/MQTT, no sólo el cable o el radio.
- Pensar que las 7 capas del IoTWF son todas igual de "físicas": sólo las 3 primeras
  son OT; las 4 últimas son la perspectiva IT/comercial.
- Olvidar que "más es más" no es el objetivo: se busca alto desempeño con bajo
  consumo de energía (relevante también para el tema de smart objects en
  [Edge, Fog y Cloud computing](/topics/edge-fog-cloud)).
