## Idea
Tres mecanismos de MQTT resuelven, cada uno, un problema distinto de "¿qué pasa si algo
no está conectado en el momento justo?": el mensaje **retained** le da a un cliente nuevo
el último valor de un tópico sin esperar el próximo publish; la **sesión persistente**
guarda mensajes pendientes para un cliente que está offline; y el **Last Will** avisa a
los demás cuando un cliente se cae sin despedirse.

## Conceptos

### Mensaje retenido (retained)
- Guarda el **último mensaje por tópico** (uno solo).
- Se almacena **en el broker**.
- Se envía **inmediatamente** a cualquier cliente nuevo que se suscriba a ese tópico.
- Representa el **estado actual** de ese tópico.

Ejemplo de la slide: un publisher envía a `home/livingroom/temperature` el payload
`"Temperature = 22°C"` con RETAIN=1. El broker lo guarda como el último retenido de ese
tópico. Cuando un cliente nuevo se suscribe a `home/livingroom/temperature`, el broker le
manda de inmediato ese mensaje guardado — sin esperar un PUBLISH nuevo.

### Sesión persistente
- Guarda **mensajes pendientes por cliente** (no por tópico).
- Actúa como un **buffer privado** para cada cliente.
- Se usa cuando el cliente está **offline**.
- Entrega los mensajes cuando el cliente **se reconecta**.
- Funciona con **QoS 1 y QoS 2** (que sí quedan guardados hasta confirmarse; QoS 0 no
  tiene esta garantía porque nunca se almacena).
- Se activa con el flag **Clean Session** del CONNECT: Clean Session = 0 mantiene la
  sesión (y su cola) entre reconexiones; Clean Session = 1 empieza siempre de cero.

### Retained vs. persistent session

| | Retained | Persistent session |
|---|---|---|
| Qué guarda | El último mensaje de un tópico | Mensajes pendientes de un cliente específico |
| Cuántos | Uno por tópico | Varios, uno por cada mensaje pendiente |
| Para quién | Cualquier cliente nuevo que se suscriba | Sólo ese cliente, cuando se reconecta |
| Qué representa | El estado actual del tópico | Un histórico de entregas no completadas |
| Depende de QoS | No (aplica igual) | Sólo QoS 1 y 2 |

### Last Will and Testament (LWT)
Se configura **en el propio CONNECT** (will topic + will message). Si el cliente se
desconecta **inesperadamente** (no manda DISCONNECT, y el broker detecta la caída por el
timeout de keep alive), el broker publica ese mensaje en el will topic en su nombre.

Como el LWT decide qué pasa cuando un cliente "desaparece", debe protegerse igual que
cualquier otro mensaje: si no está cifrado/autenticado, un atacante podría simular
desconexiones falsas (ver [Tópicos y seguridad](/topics/mqtt/subtopics/topicos-y-seguridad)).

## Método paso a paso
Frente a un requisito de "que el sistema recuerde/avise algo", preguntarse:

1. ¿Necesito que un cliente nuevo vea el último estado sin esperar? → RETAIN=1.
2. ¿Necesito que un cliente que estuvo offline reciba lo que se perdió al reconectarse?
   → sesión persistente (Clean Session=0) + QoS 1/2.
3. ¿Necesito que otros se enteren si este cliente se cae sin avisar? → Last Will en el CONNECT.

## Errores típicos
- Confundir retained (estado de un tópico, en el broker) con persistent session (cola de
  un cliente, privada).
- Pensar que el Last Will se dispara con cualquier desconexión: sólo con una
  **inesperada** (detectada por el broker); un DISCONNECT ordenado no lo activa.
- Olvidar que la sesión persistente sólo tiene sentido con QoS 1 o 2 (QoS 0 no se guarda).

**c) RETAIN=1.** El sensor debe publicar su temperatura con el flag RETAIN=1. Así, el
broker guarda ese mensaje como el último valor del tópico y lo entrega de inmediato al
panel de monitoreo apenas éste se suscribe, sin tener que esperar la siguiente
publicación cada 5 s.

**d) Last Will.** Se logra con un Last Will (Testament) configurado en el paquete CONNECT
del sensor: se define un will topic y un will message ("Sensor desconectado"). Si el
sensor se desconecta de forma inesperada (el broker lo detecta porque no llega tráfico
dentro del intervalo de keep alive), el broker publica automáticamente ese mensaje en el
tópico configurado, avisando a los suscriptores.
