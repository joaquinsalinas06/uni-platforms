## Idea

Elegida la tecnología de radio (tema anterior), falta decidir **cómo conversan** los
dispositivos: ¿cada "thing" le pide datos a un servidor cuando los necesita (cliente-servidor),
o publica lo que mide y deja que quien esté interesado se suscriba (publicar/suscribir)? Son
dos modelos de transmisión distintos, con distinta forma de escalar cuando el sistema crece
de unos pocos sensores a miles.

## Conceptos

### Cliente-servidor

Estructura de aplicación distribuida que reparte el trabajo entre servidores y clientes: el
**cliente inicia la comunicación**, el servidor responde. En la web esto se implementa con
**HTTP** y sus métodos (`GET`, `POST`, `PUT`, `DELETE`), que combinados con otras convenciones
forman un **servicio RESTful (REST API)**.

| Método | Uso típico en IoT |
|---|---|
| `GET` | Leer el valor actual de un sensor |
| `POST` | Crear un nuevo recurso (registrar un dispositivo, enviar una lectura nueva) |
| `PUT` | Actualizar un recurso existente (cambiar el estado de un actuador) |
| `DELETE` | Eliminar un recurso (dar de baja un dispositivo) |

**Pros**: concentra el procesamiento en el servidor; los clientes solo hablan con uno o varios
servidores de confianza (modelo simple de entender y asegurar).

servidor debe mantener muchas conexiones simultáneas. **Escenario de escalamiento**: ¿qué pasa
con este paradigma cuando crecen los sensores, actuadores y datos?

### Publicar/suscribir (pub/sub)

Modelo de mensajería donde los editores (**publishers**) no programan mensajes hacia clientes
específicos: **categorizan los mensajes publicados en clases (topics)**, sin que el
suscriptor tenga que pedir nada primero. Un **evento** ocurre cuando el publisher postea un
mensaje y los subscribers quedan notificados del contenido nuevo — el publisher usa un canal
de comunicación y el mensaje se copia a cada suscriptor.

En un proyecto IoT:
- **Broker**: puede ser una función del gateway local o estar en la nube. Recibe información
  de los clientes y la redirige o procesa.
- **Publisher**: se conecta al broker para publicar datos (ej. un sensor).
- **Subscriber**: dispositivos, aplicaciones o servicios que necesitan los datos; se conectan
  al broker para que les avisen de contenido nuevo.

### Alternativas al cliente-servidor puro

Frente al problema de escalar cliente-servidor, en IoT se usan tres alternativas (no
excluyentes entre sí):

- **Publicar/suscribir (ej. MQTT)**: los dispositivos no dependen directamente de un servidor
  fijo; mejor escalabilidad porque el broker desacopla a quién publica de quién consume.
- **Computación en el borde (Edge/Fog)**: se procesan los datos cerca del dispositivo,
  reduciendo la carga que llega a la nube.
- **Modelos híbridos o P2P**: evitan un único punto de falla, combinando procesamiento local
  con la nube según haga falta.

## Método paso a paso

**Cómo elegir el modelo de transmisión para un subsistema IoT**:

1. **¿Quién necesita iniciar la conversación?** Si el cliente pide datos puntuales bajo
   demanda (ej. una app que consulta el estado de un sensor cuando el usuario abre la
   pantalla) → cliente-servidor / REST. Si son muchos dispositivos que generan datos todo el
   tiempo y varios interesados en consumirlos → pub/sub.
2. **¿Cuántos consumidores va a tener el mismo dato?** Uno o pocos, conocidos de antemano →
   cliente-servidor directo. Varios, que pueden cambiar con el tiempo (se agregan
   dashboards, alertas, analítica) → pub/sub, así el publisher no cambia cuando cambian los
   suscriptores.
3. **¿Cómo va a escalar?** Si el número de dispositivos va a crecer mucho, evita que todos
   abran conexión directa a un único servidor: usa un broker (pub/sub) o procesa parte de los
   datos en el borde (edge/fog) antes de que lleguen a la nube.
4. **¿Dónde vive el broker/servidor?** Si la latencia importa y hay conectividad local
   confiable, ponlo en el gateway; si no hay restricción de latencia y se quiere centralizar
   el análisis, ponlo en la nube.

## Ejemplo resuelto

Un invernadero tiene 200 sensores de humedad publicando cada 30 segundos, y tres consumidores:
el panel de control local, una app móvil y un servicio de analítica en la nube.

- **Con cliente-servidor puro**: cada uno de los 200 sensores tendría que saber la dirección
  de cada consumidor y abrir una conexión con cada uno — 200 × 3 = 600 conexiones a mantener,
  y si se agrega un cuarto consumidor hay que reprogramar los 200 sensores.
- **Con pub/sub**: cada sensor publica una sola vez al topic `invernadero/humedad/<id>` en el
  broker del gateway. Los tres consumidores se suscriben a ese topic. Si mañana se agrega un
  cuarto consumidor, solo se suscribe al broker — ningún sensor cambia. El broker en el
  gateway también permite que el panel de control local reciba el dato sin depender de que
  haya Internet en ese momento (edge).

## Errores típicos

- Confundir "REST" con "HTTP": REST es un estilo arquitectónico que se construye combinando
  métodos HTTP con convenciones (recursos, URIs, códigos de estado); HTTP es el protocolo de
  transporte que lo hace posible.
- Pensar que pub/sub elimina el problema de escalar: el broker sigue siendo un punto que hay
  que dimensionar (aunque desacopla publishers de subscribers, no los hace infinitos).
- Meter el broker en la nube "por defecto" cuando el proyecto necesita baja latencia local:
  si el control tiene que ser rápido y no puede depender de Internet, el broker debe vivir en
  el gateway.
- Olvidar que en cliente-servidor **el cliente siempre inicia**: un servidor no puede "avisar"
  a un cliente si este no abre la conexión (por eso pub/sub resuelve mejor el caso de
  notificaciones espontáneas).

**1. Modelo usado y su problema.**

|---|---|---|
| Quién inicia | Cada sensor abre conexión HTTP | Cada sensor publica una vez |
