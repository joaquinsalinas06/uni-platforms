## Idea
LoRa solo define cómo se modula. **LoRaWAN** es el protocolo LPWAN que opera en una capa
superior y organiza la red: estructura, seguridad, autenticación y coordinación entre
dispositivos y servidores, para desplegar IoT a gran escala *(Sem10#36, Sem12_LoRa#18)*.

## Conceptos

### Arquitectura *(Sem10#28, #38, #45–46; Sem12_LoRa#47)*

- **Nodos finales** (end devices): sensan, procesan, envían y reciben (bidireccional), a batería
  durante meses o años.
- **Gateway: solo un relay.** Los paquetes del nodo **no llevan dirección destino** (ahorra
  bytes) y **no hay asociación** nodo–gateway; varios gateways pueden recibir el mismo mensaje,
  pero **solo uno debe responder**: lo decide el network server.
- **Network server**: LoRaWAN no especifica su comportamiento; mantiene baja la carga de la red
  enviando **comandos MAC** (p. ej. `LinkADRReq` pide al nodo adaptar su tasa: ADR). Cada nodo está
  asociado a un servidor, que debe manejar **millones** de dispositivos.
- **Application server**: recibe los datos de la aplicación.

### Datos clave *(Sem10#37; Sem12_LoRa#21)*
Tasas de 300 bps a 5.5 kbps (Sem10) / 0.3 a 50 kbps según SF (deck LoRa); comunicación
bidireccional segura, movilidad y localización; cifrado **AES-128** extremo a extremo con
**AppSKey** y **NwkSKey**; **ADR** (*Adaptive Data Rate*) optimiza energía y capacidad; miles de
nodos por gateway.

### Direccionamiento (no IP) *(Sem10#28, #44)*
- **DevEUI / AppEUI**: identificadores únicos de **64 bits**.
- **DevAddr**: dirección de **32 bits** del nodo dentro de la red actual, asignada por el network
  server = **AddrPrefix** (tamaño variable $N \in [7, 25]$ bits, derivado del NetID del servidor)
  + **NwkAddr** (dirección de red asignada por el network server).

| | Clase A | Clase B | Clase C |
|---|---|---|---|
| Ventanas RX | tras cada uplink | ping slots programados + tras uplinks | casi continuas |
| Consumo | muy bajo | medio | alto |
| Latencia de downlink | potencialmente alta | más predecible | generalmente baja |
| Beacon | no | **sí** | no |
| Batería | la más larga | intermedia | la más corta |
| Aplicación típica | sensores a batería | sensores/actuadores con downlinks programados | actuadores enchufados que requieren downlink rápido |
| Ventaja | máxima eficiencia | oportunidades de downlink predecibles | espera mínima |
| Limitación | el downlink espera al próximo uplink | requiere sincronización | alto consumo |

## Método paso a paso
**Elegir clase** según el enunciado:
1. ¿El servidor necesita mandar órdenes en cualquier momento y con poca latencia? → **C** (si hay
   alimentación de red).
2. ¿Necesita órdenes en horarios conocidos y el nodo es a batería? → **B**.
3. ¿El nodo solo reporta y las respuestas pueden esperar al próximo uplink? → **A**.

## Ejemplo resuelto
*(derivado de la tabla)* Una válvula de riego enchufada que debe cerrarse en cuanto el operador
lo pida → **clase C**. Un sensor de humedad a batería que reporta cada hora → **clase A**: el
eventual cambio de configuración puede esperar a la ventana tras el próximo uplink.

## Errores típicos
- Decir que el gateway decide a quién responder: lo decide el **network server**.
- Asignar direcciones IP a los nodos LoRaWAN: usan DevEUI/DevAddr.
- Creer que clase B no tiene las ventanas de A: B y C son "A + algo".

## Pregunta tipo examen

<ExerciseBlock client:visible exercise={{
  level: 2,
  statement: "Un mismo uplink de un nodo LoRaWAN llega a tres gateways. ¿Qué hace cada gateway, quién decide la respuesta y qué clase usaría si el nodo es una alarma a batería que solo reporta eventos?",
  hints: [
    "¿El paquete lleva dirección destino? ¿Hay asociación nodo-gateway?",

    "La clase de menor consumo abre ventanas solo tras su propio uplink.",

1. **Gateways:** son solo relays; los tres reenvían el paquete al network server (el paquete
   no tiene destino ni hay asociación nodo–gateway).
2. **Network server:** descarta duplicados y **elige el mejor gateway** para responder (solo uno
   debe hacerlo); también puede pedir adaptar la tasa con `LinkADRReq`.
3. **Clase A:** el nodo solo reporta; cualquier respuesta llega en RX1/RX2 tras su uplink, con el
   menor consumo y la batería más larga.
