## Idea

Un dispositivo IoT necesita conversar con un servidor, una nube o con otros
dispositivos. No existe un protocolo de aplicación único para hacerlo: la
elección depende de cuánta memoria y cómputo tiene el dispositivo, si la red
es confiable, si se necesita una respuesta inmediata o si basta con avisar y
seguir. Esta página compara los protocolos de aplicación que no son MQTT
(que se estudia aparte, en [MQTT](/topics/mqtt)) y da un criterio para elegir
uno según el escenario.

## Conceptos

### No hay un protocolo universal

Las slides lo dicen de forma literal: *"There is no such protocol!"* Ningún
protocolo de datos es estándar para todas las aplicaciones IoT; la elección
cambia según los parámetros de diseño. Los protocolos de aplicación en IoT se
agrupan en dos categorías, según el modelo de comunicación (visto la semana
anterior):

- **Cliente/servidor**: el dispositivo envía una petición y espera una
  respuesta directa de un servidor. Ejemplos: **HTTP**, **CoAP**.
- **Publicador/suscriptor**: existe una entidad central, el **broker**, que
  recibe mensajes de publicadores y los reenvía a los suscriptores
  interesados, sin que unos conozcan a otros. Ejemplos: **WebSocket** (cuando
  se usa así), **AMQP**, **MQTT**.

### HTTP

HTTP (HyperText Transfer Protocol) es un protocolo de **petición/respuesta**
sobre el paradigma cliente-servidor: el cliente envía una petición HTTP y el
servidor responde con datos (HTML, JSON, etc.). Es el protocolo base de la
web y trabaja siempre por parejas: una petición, una respuesta, conexión que
después se cierra (o se reutiliza, pero no queda "abierta" para que el
servidor hable espontáneamente).

Los métodos HTTP representan la acción sobre un recurso:

| Método | Efecto | Ejemplo |
|---|---|---|
| `GET` | Solicita un recurso, no modifica nada | Leer el estado de un sensor |
| `POST` | Envía datos para crear un recurso | Registrar una nueva lectura |
| `PUT` | Reemplaza completamente un recurso | Fijar la velocidad de un motor |
| `DELETE` | Elimina un recurso | Borrar una regla de automatización |

**REST para controlar dispositivos**: REST (Representational State Transfer)
se apoya en HTTP y sus métodos. Cada dispositivo o recurso (un foco, un
motor, un sensor de temperatura) se representa como una **URL (endpoint)**,
y las operaciones de control o consulta se hacen con el método HTTP
correspondiente:

- `GET /devices/led1/status` → lee si el foco `led1` está encendido.
- `POST /devices/led1/on` → enciende el foco `led1`.
- `PUT /devices/motor2/speed` (cuerpo `{"speed": 120}`) → fija la velocidad
  del motor `motor2`.
- `DELETE /devices/rule7` → elimina la regla de automatización `rule7`.

### WebSocket

WebSocket permite crear un **canal de comunicación bidireccional**
cliente-servidor. A diferencia de HTTP (unidireccional: el cliente pide, el
servidor responde), una conexión WebSocket, tras un *handshake* inicial entre
cliente y servidor, **permanece abierta** hasta que alguno de los dos la
cierra.

Beneficios frente a HTTP: **baja latencia**, **conexión persistente** y
**full-duplex** (los dos lados transmiten a la vez, no por turnos). Se usa
cuando se necesita una conexión abierta por mucho tiempo para intercambiar
datos constantemente: feeds de redes sociales, chats, edición colaborativa,
juegos multijugador — y, en IoT, paneles de control que reciben datos de
sensores en tiempo real.

### CoAP

CoAP (Constrained Application Protocol) se diseñó para dispositivos con
**restricciones importantes**: poca capacidad de cómputo, poca memoria, o que
no pueden usar los protocolos habituales de redes de computadoras. Se basa en
una arquitectura **REST**, igual que HTTP, pero se diferencia en dos puntos
clave:

- Usa **UDP** como transporte (no TCP), con mensajes pequeños y poco
  *overhead* — ideal para dispositivos de poca memoria y poco cómputo.
- El dispositivo puede ser **cliente o servidor a la vez**: no hay una
  jerarquía fija como en HTTP clásico.

Se usa en aplicaciones industriales, automatización residencial, gestión
M2M (máquina a máquina) y comunicación satelital (poco ancho de banda).

La diapositiva original dibuja esto como cuatro bloques apilados, de abajo
hacia arriba: `UDP` → `Messages` → `Request/Responses` → `Application`, con
el nombre `CoAP` señalando las dos capas intermedias (Messages y Request/
Responses son las que CoAP agrega sobre UDP para ofrecer una interfaz REST).

Un intercambio típico: cualquiera de los dos extremos puede iniciar la
petición, porque ambos pueden actuar como servidor.

### AMQP

AMQP (Advanced Message Queuing Protocol) usa **TCP** como transporte y
permite envío y recepción **asíncrona** de mensajes: puede entenderse como el
equivalente asíncrono de HTTP, donde un cliente contacta a un **broker** "a
mitad de camino" en vez de hablar directo con el destino final.

AMQP nació en la comunidad financiera, con el objetivo de permitir
interoperabilidad entre dispositivos y soporte multi-SO. **RabbitMQ** es la
aplicación tipo broker más conocida para AMQP.

El broker organiza el enrutamiento con tres piezas:

- **Exchange**: recibe lo que publica el *publisher*.
- **Bindings**: reglas que dicen a qué colas debe ir cada mensaje según el
  exchange.
- **Queue**: donde el mensaje espera hasta que un *consumer* lo consume.

### MQTT (adelanto)

MQTT también es publicador/suscriptor y también usa TCP, pero está pensado
específicamente para dispositivos de poca memoria y poco ancho de banda. Su
encabezado, sus niveles de QoS y su ciclo de vida se estudian en detalle en
[MQTT](/topics/mqtt) — no se repiten aquí.

### Comparación

| Protocolo | Transporte | Modelo | Encabezado | Confiabilidad | Uso típico |
|---|---|---|---|---|---|
| HTTP | TCP | Cliente/servidor | Grande (texto, variable) | Alta (TCP + reintento en la app) | APIs REST, paneles web, control puntual de dispositivos |
| WebSocket | TCP | Bidireccional (pub/sub o punto a punto) | Chico tras el handshake | Alta (TCP) | Datos en tiempo real, paneles con refresco continuo |
| CoAP | UDP | Cliente/servidor (ambos roles) | Muy chico | Media (UDP; CoAP puede pedir confirmación, CON/ACK) | Dispositivos muy restringidos, M2M, satelital |
| AMQP | TCP | Publicador/suscriptor (broker) | Medio | Alta (TCP + colas persistentes) | Mensajería empresarial, integración de sistemas heterogéneos |
| MQTT | TCP | Publicador/suscriptor (broker) | Muy chico (2–5 bytes) | Configurable por QoS (0/1/2) | Telemetría IoT, sensores de bajo consumo |

## Método paso a paso

Para elegir un protocolo de aplicación ante un escenario dado:

1. **¿Qué tan restringido es el dispositivo?** Poca RAM/CPU y quieres el
   encabezado más chico posible → CoAP o MQTT (nunca HTTP "pesado").
2. **¿Necesitas que el servidor hable primero, sin que el cliente pregunte?**
   Si sí, HTTP puro no alcanza (es petición/respuesta) → WebSocket (canal
   abierto) o un modelo pub/sub (AMQP, MQTT).
3. **¿El transporte puede ser no confiable (UDP)?** Si el escenario tolera
   perder algún paquete y prioriza velocidad/bajo consumo → CoAP. Si necesitas
   la garantía de entrega de TCP → HTTP, WebSocket, AMQP o MQTT.
4. **¿Hay un broker desacoplando emisores de receptores?** Si el publicador
   no debe conocer a sus consumidores (y pueden ser varios, o ninguno) →
   pub/sub (AMQP o MQTT). Si es una consulta directa a un recurso conocido →
   cliente/servidor (HTTP o CoAP).
5. **¿El origen es una integración empresarial con colas y enrutamiento
   complejo (varias colas, varias reglas)?** → AMQP. **¿Es telemetría de
   sensores con encabezado mínimo?** → MQTT.

## Ejemplo resuelto

**Escenario**: una red de 200 sensores de humedad de suelo, alimentados por
batería, que reportan una lectura cada 10 minutos a un servidor en la nube.
El enlace es una red celular con cobertura intermitente.

1. *¿Qué tan restringido es el dispositivo?* Mucho: batería y poco cómputo →
   se descarta HTTP por su encabezado grande y su modelo de conexión por
   petición.
2. *¿Necesita el servidor hablar primero?* No: solo reporta lecturas.
3. *¿Hay un broker que desacople a los 200 sensores de quien consume los
   datos (dashboard, base de datos, alertas)?* Sí, conviene: así el sensor no
   necesita saber quién procesa sus datos.
4. *¿UDP es aceptable?* La cobertura es intermitente: conviene la garantía de
   entrega de TCP con reconexión, más que UDP puro.

**Conclusión**: MQTT (pub/sub, TCP, encabezado mínimo, QoS configurable para
tolerar la cobertura intermitente) es la elección natural — ver
[MQTT](/topics/mqtt) para el detalle de QoS y del ciclo CONNECT/PUBLISH/
DISCONNECT.

## Errores típicos

- Pensar que WebSocket es "pub/sub": es un **canal bidireccional**; el
  patrón pub/sub (broker) se construye encima si se quiere, pero no viene
  incluido.
- Confundir CoAP con "HTTP sobre UDP sin más": CoAP sí es REST sobre UDP,
  pero su encabezado y su manejo de confirmaciones (CON/ACK) son distintos,
  precisamente para tolerar redes no confiables.
- Olvidar que en CoAP **ambos** extremos pueden ser cliente o servidor: no
  hay un servidor central fijo como en HTTP clásico.
- Creer que AMQP y MQTT son lo mismo por ser ambos pub/sub sobre TCP: AMQP
  tiene un modelo de enrutamiento más rico (exchange + bindings + colas
  múltiples) pensado para integración empresarial; MQTT prioriza el
  encabezado mínimo para el dispositivo final.
- Elegir un protocolo por "el más conocido" en vez de por las restricciones
  reales del dispositivo y de la red.
