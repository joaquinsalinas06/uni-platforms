## Pregunta 1 — Ping-Pong (2 pts)

a) Desarrolle un código C++-MPI: el proceso 0 envía un mensaje al proceso 1 (*ping*); recibido el mensaje, el proceso 1 envía un mensaje de nuevo al proceso 0 (*pong*). Itere el procedimiento 50 veces y mida el tiempo de comunicación por mensaje en µs. Discuta si es necesario usar desbloqueo en este problema (1 pt)

### Solución

```cpp
#include <iostream>
#include <mpi.h>

#define NUM_MSG 50

int main(int argc, char *argv[]) {
  int my_rank;
  float buffer[1];
  double start, finish, msg_transfer_time;
  MPI_Status status;

  MPI_Init(&argc, &argv);
  MPI_Comm_rank(MPI_COMM_WORLD, &my_rank);

  start = MPI_Wtime();
  for (int i = 1; i <= NUM_MSG; i++) {
    if (my_rank == 0) {
      MPI_Send(buffer, 1, MPI_FLOAT, 1, 17, MPI_COMM_WORLD);   // ping
      MPI_Recv(buffer, 1, MPI_FLOAT, 1, 23, MPI_COMM_WORLD, &status); // pong
    } else if (my_rank == 1) {
      MPI_Recv(buffer, 1, MPI_FLOAT, 0, 17, MPI_COMM_WORLD, &status); // ping
      MPI_Send(buffer, 1, MPI_FLOAT, 0, 23, MPI_COMM_WORLD);   // pong
    }
  }
  finish = MPI_Wtime();

  if (my_rank == 0) {
    msg_transfer_time = ((finish - start) / (2 * NUM_MSG)) * 1e6; // µs
    std::cout << "Tiempo por mensaje: " << msg_transfer_time << " us\n";
  }

  MPI_Finalize();
}
```

El proceso 0 alterna `Send` (ping) y `Recv` (pong), mientras el proceso 1 alterna `Recv` (ping) y `Send` (pong): las directivas están emparejadas en orden opuesto entre ambos ranks, exactamente el orden seguro visto en clase para evitar bloqueo mutuo. **No es necesario usar desbloqueo (comunicación no bloqueante)** en este problema: al ser solo dos procesos con roles fijos y complementarios (uno inicia con Send, el otro con Recv), no existe riesgo de deadlock — cada `Send` siempre encuentra un `Recv` ya esperando del lado contrario. Usar `MPI_Isend`/`MPI_Irecv` no cambiaría el resultado porque no hay cómputo independiente que solapar con la comunicación en este patrón puramente secuencial de ida y vuelta.

b) Mida la latencia y ancho de banda para dos modos de comunicación (`MPI_Send`, `MPI_Ssend`), y mensajes de tamaño 8 B, 512 B, 32 kB y 2 MB. Realice suficientes pruebas para que el resultado sea confiable, excluyendo primeras iteraciones. Genere una gráfica de tiempo vs. $n$ e interprete los resultados. (1 pt)

### Solución

```cpp
#include <iostream>
#include <vector>
#include <mpi.h>

void measure(int size_bytes, bool use_ssend, int my_rank, int reps = 100, int warmup = 10) {
  std::vector<char> buf(size_bytes);
  MPI_Status status;
  double t0, t1, total = 0.0;

  for (int i = 0; i < warmup + reps; i++) {
    MPI_Barrier(MPI_COMM_WORLD);
    t0 = MPI_Wtime();
    if (my_rank == 0) {
      if (use_ssend) MPI_Ssend(buf.data(), size_bytes, MPI_CHAR, 1, 0, MPI_COMM_WORLD);
      else           MPI_Send (buf.data(), size_bytes, MPI_CHAR, 1, 0, MPI_COMM_WORLD);
      MPI_Recv(buf.data(), size_bytes, MPI_CHAR, 1, 1, MPI_COMM_WORLD, &status);
    } else if (my_rank == 1) {
      MPI_Recv(buf.data(), size_bytes, MPI_CHAR, 0, 0, MPI_COMM_WORLD, &status);
      if (use_ssend) MPI_Ssend(buf.data(), size_bytes, MPI_CHAR, 0, 1, MPI_COMM_WORLD);
      else           MPI_Send (buf.data(), size_bytes, MPI_CHAR, 0, 1, MPI_COMM_WORLD);
    }
    t1 = MPI_Wtime();
    if (i >= warmup) total += (t1 - t0);
  }

  if (my_rank == 0) {
    double avg_rtt = total / reps;
    double one_way = avg_rtt / 2.0;
    double bw = size_bytes / one_way / 1e6; // MB/s
    std::cout << (use_ssend ? "Ssend " : "Send  ") << "n=" << size_bytes
              << " B  t=" << one_way * 1e6 << " us  BW=" << bw << " MB/s\n";
  }
}

int main(int argc, char** argv) {
  MPI_Init(&argc, &argv);
  int my_rank; MPI_Comm_rank(MPI_COMM_WORLD, &my_rank);
  int sizes[] = {8, 512, 32*1024, 2*1024*1024};
  for (bool ssend : {false, true})
    for (int s : sizes) measure(s, ssend, my_rank);
  MPI_Finalize();
}
```

**Interpretación esperada.** El tiempo de un mensaje sigue el modelo $T(x) = \alpha + x\beta$, donde $\alpha$ es la latencia (intersección en $x=0$) y $\beta$ el tiempo por byte (pendiente, inverso del ancho de banda). Con `MPI_Send` los mensajes pequeños (8 B, 512 B) usan el protocolo *eager* y muestran un tiempo cercano a la latencia pura $\alpha$, prácticamente independiente del tamaño; con `MPI_Ssend`, incluso los mensajes pequeños exigen la sincronización del protocolo *rendezvous* (esperar a que el receptor llame a `Recv`), por lo que su tiempo para mensajes chicos es mayor que el de `Send`. Para mensajes grandes (32 kB, 2 MB), ambos superan el umbral eager de la implementación y `Send` se comporta internamente como `Ssend`: los tiempos convergen y la curva se vuelve dominada por el término $x\beta$ (pendiente = $1/\text{ancho de banda}$). En una gráfica de tiempo vs. $n$ (escala log-log), se espera una región plana a bajo $n$ (dominada por $\alpha$) y una región lineal a partir del umbral eager (dominada por $\beta$), con `Ssend` sistemáticamente por encima de `Send` en la región de mensajes pequeños.

## Pregunta 2 — Vectores (2 pts)

El código adjunto (`Ej02_vectores_sec.cpp`) realiza el siguiente cálculo vectorial:
$$C[j] = \sum_{i=0}^{N-1} A[j][i]\cdot B[j][i], \quad j=0,1,\dots,M-1$$
para una cantidad $M$ de vectores, cada uno de tamaño $N$, obteniendo un array $C$ de tamaño $M$.

**2.1)** Paralelice el código con MPI bloqueado (debe ser compilable y estar correctamente paralelizado) y discuta maneras de optimizar el cálculo. (0.5 pts)

### Solución

```cpp
#include <vector>
#include <iostream>
#include <mpi.h>

int main(int argc, char** argv) {
  MPI_Init(&argc, &argv);
  int my_rank, p;
  MPI_Comm_rank(MPI_COMM_WORLD, &my_rank);
  MPI_Comm_size(MPI_COMM_WORLD, &p);

  long long M = 1 << 10, N = 1 << 17;
  long long M_loc = M / p; // asumimos p | M

  std::vector<double> A, B, C;
  std::vector<double> A_loc(M_loc * N), B_loc(M_loc * N), C_loc(M_loc, 0.0);

  if (my_rank == 0) {
    A.resize(M * N); B.resize(M * N); C.resize(M, 0.0);
    for (long long j = 0; j < M; ++j)
      for (long long i = 0; i < N; ++i) {
        A[j*N + i] = 1.0 + (i % 7) * 0.01 + j * 0.001;
        B[j*N + i] = 2.0 + (i % 5) * 0.02 + j * 0.002;
      }
  }

  // Reparte bloques de M_loc vectores completos (M_loc*N elementos) por proceso
  MPI_Scatter(A.data(), M_loc*N, MPI_DOUBLE, A_loc.data(), M_loc*N, MPI_DOUBLE, 0, MPI_COMM_WORLD);
  MPI_Scatter(B.data(), M_loc*N, MPI_DOUBLE, B_loc.data(), M_loc*N, MPI_DOUBLE, 0, MPI_COMM_WORLD);

  for (long long j = 0; j < M_loc; ++j) {
    double acc = 0.0;
    const long long base = j * N;
    for (long long i = 0; i < N; ++i)
      acc += A_loc[base + i] * B_loc[base + i];
    C_loc[j] = acc;
  }

  MPI_Gather(C_loc.data(), M_loc, MPI_DOUBLE, C.data(), M_loc, MPI_DOUBLE, 0, MPI_COMM_WORLD);

  MPI_Finalize();
}
```

Se distribuyen $A$ y $B$ por bloques de vectores completos (cada proceso recibe $M/p$ filas contiguas de tamaño $N$), pues cada $C[j]$ solo depende de la fila $j$ de $A$ y $B$: no hay dependencias entre procesos, por lo que ni `Scatter` de $A$ ni de $B$ requieren coordinación adicional. El resultado se recolecta con `MPI_Gather`. Como optimización, se podría: (i) usar `MPI_Scatterv`/`MPI_Gatherv` si $M$ no es divisible por $p$; (ii) usar tipos derivados o un solo buffer intercalado para enviar $A$ y $B$ en una única comunicación y reducir el número de llamadas colectivas; (iii) solapar la comunicación de `B_loc` con el cómputo parcial sobre `A_loc` usando `MPI_Iscatter` (no bloqueado).

**2.2)** Determine la complejidad del algoritmo considerando cómputo y comunicación (1 pt)

### Solución

*Comunicación.* Dos `Scatter` de $MN/p$ elementos cada uno y un `Gather` de $M/p$ elementos:
$$T_{comm} = O\!\left(2\log p\left(\alpha+\frac{MN}{p}\beta\right) + \log p\left(\alpha+\frac{M}{p}\beta\right)\right) \approx O\!\left(\log p\left(\alpha+\frac{MN}{p}\beta\right)\right)$$
(el término dominante es la distribución de $A$ y $B$, ya que $N \gg 1$).

*Cómputo.* Cada proceso realiza $M/p$ productos punto de tamaño $N$: $O(MN/p)$.

$$T_p(M,N,p) = O\!\left(\frac{MN}{p} + \log p\left(\alpha+\frac{MN}{p}\beta\right)\right)$$

## Pregunta 3 — Suavizado (2 pts)

int main(int argc, char** argv) {
    long long N = 1LL << 20;
    std::vector<double> global_in(N), global_out(N, 0.0);
    for (long long i = 0; i < N; ++i) global_in[i] = double(i % 101);
    double t_update = 0.0;
    auto t0 = std::chrono::high_resolution_clock::now();
    global_out[0] = (global_in[0] + global_in[0] + global_in[1]) / 3.0;
    for (long long i = 1; i <= N - 2; ++i) {
        global_out[i] = (global_in[i-1] + global_in[i] + global_in[i+1]) / 3.0;
    }
    global_out[N-1] = (global_in[N-2] + global_in[N-1] + global_in[N-1]) / 3.0;
    t_update = std::chrono::duration<double>(t1 - t0).count();

**3.1)** Complete el código con directivas MPI no bloqueadas para que funcione en paralelo. El código no necesita compilar, pero las directivas deben tener todos sus parámetros. (0.5 pts)

### Solución

Cada proceso trabaja sobre un bloque local de $N/p$ elementos y necesita un valor "halo" de cada vecino (el elemento de borde de la partición vecina) para calcular su propio elemento de borde. Se usan directivas no bloqueadas para solapar el intercambio de halos con el cómputo interno:

```cpp
int p, my_rank;
MPI_Comm_size(MPI_COMM_WORLD, &p);
MPI_Comm_rank(MPI_COMM_WORLD, &my_rank);
long long N = 1LL << 20;
long long N_loc = N / p;

std::vector<double> in_loc(N_loc + 2), out_loc(N_loc); // +2: halos izq/der
for (long long i = 0; i < N_loc; ++i)
    in_loc[i+1] = double(((my_rank * N_loc) + i) % 101);

int left  = (my_rank == 0)     ? MPI_PROC_NULL : my_rank - 1;
int right = (my_rank == p - 1) ? MPI_PROC_NULL : my_rank + 1;

MPI_Request reqs[4];
// Intercambio no bloqueado de halos
MPI_Isend(&in_loc[1],       1, MPI_DOUBLE, left,  0, MPI_COMM_WORLD, &reqs[0]);
MPI_Isend(&in_loc[N_loc],   1, MPI_DOUBLE, right, 1, MPI_COMM_WORLD, &reqs[1]);
MPI_Irecv(&in_loc[0],       1, MPI_DOUBLE, left,  1, MPI_COMM_WORLD, &reqs[2]);
MPI_Irecv(&in_loc[N_loc+1], 1, MPI_DOUBLE, right, 0, MPI_COMM_WORLD, &reqs[3]);

// Bordes globales clonados (proceso 0 y proceso p-1)
if (my_rank == 0)     in_loc[0]       = in_loc[1];
if (my_rank == p - 1) in_loc[N_loc+1] = in_loc[N_loc];

// Cómputo de los elementos internos que NO dependen de los halos (solapado)
for (long long i = 2; i <= N_loc - 1; ++i)
    out_loc[i-1] = (in_loc[i-1] + in_loc[i] + in_loc[i+1]) / 3.0;

// Espera a que los halos lleguen antes de calcular los bordes locales
MPI_Waitall(4, reqs, MPI_STATUSES_IGNORE);
out_loc[0]       = (in_loc[0]       + in_loc[1]   + in_loc[2])   / 3.0;
out_loc[N_loc-1] = (in_loc[N_loc-1] + in_loc[N_loc]+ in_loc[N_loc+1]) / 3.0;
```

**3.2)** Determine la complejidad del algoritmo considerando cómputo y comunicación (1 pt)

### Solución

*Cómputo.* Cada proceso calcula $N/p$ promedios de 3 elementos (2 sumas + 1 división): $O(N/p)$.

*Comunicación.* Cada proceso intercambia solo 2 valores escalares (un halo a la izquierda, uno a la derecha), sin colectivas: costo constante por proceso, $O(\alpha)$ (mensaje de 1 elemento, término $\beta$ despreciable).

$$T_p(N,p) = O\!\left(\frac{N}{p} + \alpha\right)$$

**3.3)** Determine el speed-up en función de $n$ y $p$. Calcule la eficiencia del código y la condición de escalabilidad. (0.5 pts)

### Solución

El tiempo secuencial es $T(n) = O(n)$ (tres operaciones por elemento). Entonces:
$$S(n,p) = \frac{n}{n/p + \alpha} = \frac{1}{1/p + \alpha p/n}$$
$$\lim_{n\to\infty} S(n,p) = p \quad \text{(speedup lineal ideal)}$$
$$E(n,p) = \frac{S(n,p)}{p} = \frac{1}{1 + \alpha p^2/n}$$

Para que la eficiencia se mantenga aproximadamente constante al crecer $p$, se requiere la condición de escalabilidad débil $n \propto p^2$. Como la comunicación es solo de vecino a vecino (no crece con $p$, a diferencia de las colectivas de los otros ejercicios), el algoritmo escala muy bien: basta con que $n$ crezca ligeramente más rápido que $p$ para mantener eficiencia alta en la práctica.
