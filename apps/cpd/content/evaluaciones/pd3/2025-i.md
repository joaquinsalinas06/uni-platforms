## Pregunta 1 — Comunicación punto a punto (3 pts)

Complete y analice los códigos adjuntos.

**1.1)** En el código `ejercicio01.1.cpp`, compare el uso de envío sincrónico (`Ssend`) y del envío buffered (`Bsend`). Describa la comunicación observada. No tiene que garantizar la ejecución correcta en paralelo. (1 pt)

```cpp
#include <mpi.h>
#include <stdio.h>
#include <iostream>
using namespace std;

int main(int argc, char **argv) {
  int numtasks, rank, next, prev, tag1=1, tag2=2, N=1<<14;
  int sbuf[N], rbuf[N];
  double t0,t1;
  MPI_Status status;
  MPI_Init(&argc, &argv);
  MPI_Comm_rank(MPI_COMM_WORLD, &rank);
  MPI_Comm_size(MPI_COMM_WORLD, &numtasks);

  prev = rank - 1;
  next = rank + 1;
  if (rank == 0) prev = numtasks - 1;
  if (rank == (numtasks - 1)) next = 0;

  t0 = MPI_Wtime();

  // COMUNICACION CICLICA
  // 1. Envio sincronico
  MPI_Ssend(sbuf, N, MPI_INT, next, tag1, MPI_COMM_WORLD);
  MPI_Recv(rbuf, N, MPI_INT, prev, tag1, MPI_COMM_WORLD, &status);

  // Reserva espacio para el envio buffered
  int buffer_size = (MPI_BSEND_OVERHEAD + N*sizeof(int));
  void* buffer = malloc(buffer_size);
  MPI_Buffer_attach(buffer, buffer_size);

  // 2. Envio buffered
  MPI_Bsend(sbuf, N, MPI_INT, next, tag2, MPI_COMM_WORLD);
  MPI_Recv(rbuf, N, MPI_INT, prev, tag2, MPI_COMM_WORLD, &status);

  // Libera espacio reservado
  MPI_Buffer_detach(&buffer, &buffer_size);
  free(buffer);

  t1 = MPI_Wtime();
  if (rank == 0) cout << "Tiempo (s): " << t1-t0 << endl;

  MPI_Finalize();
}
```

### Solución

Cada proceso reenvía en anillo hacia `next` y recibe de `prev`. Con envío sincrónico (`MPI_Ssend`), la llamada no retorna hasta que el proceso destino haya iniciado el `MPI_Recv` correspondiente: como todos los procesos del anillo ejecutan primero el `Send` y luego el `Recv`, **ninguno llega nunca a su `Recv`**, y el programa se bloquea mutuamente (deadlock), sin importar el tamaño del mensaje.

El envío buffered (`MPI_Bsend`) copia el mensaje a un búfer intermedio reservado con `MPI_Buffer_attach` y retorna de inmediato, sin esperar a que el receptor esté listo. Esto rompe el bloqueo mutuo, **pero solo si el mensaje cabe en el búfer** reservado (`MPI_BSEND_OVERHEAD + N*sizeof(int)`); si el mensaje fuera más grande que el espacio disponible, `MPI_Bsend` fallaría o el comportamiento dejaría de ser no bloqueante en la práctica.

**1.2)** Describa el funcionamiento de los códigos `ejercicio01.2a.cpp` y `ejercicio01.2b.cpp` al enviar los datos de temperatura y masa de un proceso a otro. Si encuentra un error en cada uno, corríjalo. (1 pt)

```cpp
// ejercicio01.2a.cpp (original, con error)
if (my_rank == 0) {
  temp = 100;  mass = 2.5;
  MPI_Send(&temp, 1, MPI_FLOAT, 1, 17, MPI_COMM_WORLD);
  MPI_Send(&mass, 1, MPI_FLOAT, 1, 18, MPI_COMM_WORLD);
} else if (my_rank == 1) {
  MPI_Recv(&mass, 1, MPI_FLOAT, 0, 17, MPI_COMM_WORLD, &status); // tag cruzado
  printf("I am process %i and received mass=%3.1f \n", my_rank, mass);
  MPI_Recv(&temp, 1, MPI_FLOAT, 0, 18, MPI_COMM_WORLD, &status); // tag cruzado
  printf("I am process %i and received temp=%3.0f \n", my_rank, temp);
}
```

### Solución

En `ejercicio01.2a.cpp`, el proceso 0 envía `temp` con tag 17 y `mass` con tag 18, pero el proceso 1 recibe el mensaje de tag 17 en la variable `mass` y el de tag 18 en `temp`: los valores llegan intercambiados. **Los tags de cada variable deben coincidir** para que la comunicación sea correcta, y además el orden en que se emparejan Send/Recv debe respetar esa correspondencia:

```cpp
} else if (my_rank == 1) {
  MPI_Recv(&temp, 1, MPI_FLOAT, 0, 17, MPI_COMM_WORLD, &status);
  printf("I am process %i and received temp=%3.0f \n", my_rank, temp);
  MPI_Recv(&mass, 1, MPI_FLOAT, 0, 18, MPI_COMM_WORLD, &status);
  printf("I am process %i and received mass=%3.1f \n", my_rank, mass);
}
```

En `ejercicio01.2b.cpp` el mismo error de tags está presente (arreglos `temp`/`mass` de tamaño `LNG=5000`), y se corrige igual. Además, al enviar arreglos de `LNG=5000` floats (20 000 bytes), el tamaño supera el umbral *eager* del protocolo interno de MPI y la comunicación se vuelve **sincrónica** (modo *rendezvous*): el `MPI_Send` del proceso 0 se bloquea hasta que el proceso 1 llegue a su `MPI_Recv` correspondiente. Reduciendo el tamaño del arreglo (por debajo del umbral eager de la implementación) se recupera el comportamiento no bloqueante original y se evita el bloqueo.

**1.3)** En el código `ejercicio01.3.cpp`, invierta la secuencia de llamadas (primero `Recv` y luego `Send` estándar) y describa qué sucede. ¿Sucede lo mismo si mantiene este orden pero el recibo es desbloqueado? Argumente su respuesta. (1 pt)

```cpp
// Original
MPI_Send(sbuf, N, MPI_INT, next, tag1, MPI_COMM_WORLD);
MPI_Recv(rbuf, N, MPI_INT, prev, tag1, MPI_COMM_WORLD, &status);
```

### Solución

Al invertir el orden (`MPI_Recv` antes que `MPI_Send`) el resultado no cambia: **se mantiene el bloqueo**, porque todos los procesos del anillo ejecutan la misma directiva bloqueante primero (ahora `Recv`), y como ninguno ha enviado todavía, todos quedan esperando indefinidamente un mensaje que nadie envía. No hay diferencia respecto al caso original.

Si en cambio se usa un recibo **desbloqueado** (`MPI_Irecv`) manteniendo el orden Recv-antes-que-Send:

```cpp
MPI_Request req;
MPI_Irecv(rbuf, N, MPI_INT, prev, tag1, MPI_COMM_WORLD, &req);
MPI_Send(sbuf, N, MPI_INT, next, tag1, MPI_COMM_WORLD);
MPI_Wait(&req, &status);
```

el `MPI_Irecv` retorna inmediatamente (solo registra la solicitud de recepción) y el proceso puede continuar hasta el `MPI_Send`, que sí puede completarse porque el destino ya "espera" el mensaje mediante la solicitud pendiente. Esto rompe el ciclo de bloqueo mutuo y la comunicación se ejecuta en paralelo, **siempre que `MPI_Wait` se ejecute después del `MPI_Send`**. Si `MPI_Wait` se colocara antes del `Send`, el proceso quedaría esperando a que la recepción se complete antes de haber enviado su propio mensaje, y el bloqueo mutuo reaparecería igual que en el caso puramente bloqueante.

## Pregunta 2 — Comunicación colectiva (2 pts)

- En `ejercicio02a.cpp`, reemplace `MPI_Allreduce` por directivas de comunicación punto a punto (1 pt).
- En `ejercicio02b.cpp`, reemplace `MPI_Gather` por directivas de comunicación punto a punto (1 pt).

Encuentre una solución bloqueada y una no bloqueada en cada caso. Compare los tiempos de comunicación en ambos códigos en cada caso, con la complejidad teórica estimada de ambos. Comente los resultados. Si es necesario, utilice la mayor cantidad de procesos posible, incluso si no cuenta con esa cantidad en su laptop.

```cpp
// ejercicio02a.cpp (original)
MPI_Allreduce(&my_rank, &sum, 1, MPI_INT, MPI_SUM, MPI_COMM_WORLD);

// ejercicio02b.cpp (original)
MPI_Gather(result_local, N, MPI_DOUBLE, result_array, N, MPI_DOUBLE, 0, MPI_COMM_WORLD);
```

### Solución

**Allreduce → punto a punto.** La forma más directa de reproducir `Allreduce` con Send/Recv es reducir hacia el proceso 0 (que recibe y suma los `size-1` valores restantes) y luego difundir el resultado de vuelta a todos.

*Versión bloqueada:*

```cpp
int my_sum = my_rank, global_sum;
if (my_rank == 0) {
  global_sum = my_sum;
  int recv_val;
  for (int p = 1; p < size; p++) {
    MPI_Recv(&recv_val, 1, MPI_INT, p, 0, MPI_COMM_WORLD, &status);
    global_sum += recv_val;
  }
  for (int p = 1; p < size; p++)
    MPI_Send(&global_sum, 1, MPI_INT, p, 1, MPI_COMM_WORLD);
} else {
  MPI_Send(&my_sum, 1, MPI_INT, 0, 0, MPI_COMM_WORLD);
  MPI_Recv(&global_sum, 1, MPI_INT, 0, 1, MPI_COMM_WORLD, &status);
}
```

*Versión no bloqueada:*

```cpp
int my_sum = my_rank, global_sum;
if (my_rank == 0) {
  std::vector<int> recv_vals(size);
  std::vector<MPI_Request> reqs(size - 1);
  for (int p = 1; p < size; p++)
    MPI_Irecv(&recv_vals[p], 1, MPI_INT, p, 0, MPI_COMM_WORLD, &reqs[p-1]);
  MPI_Waitall(size - 1, reqs.data(), MPI_STATUSES_IGNORE);
  global_sum = my_sum;
  for (int p = 1; p < size; p++) global_sum += recv_vals[p];
  std::vector<MPI_Request> sreqs(size - 1);
  for (int p = 1; p < size; p++)
    MPI_Isend(&global_sum, 1, MPI_INT, p, 1, MPI_COMM_WORLD, &sreqs[p-1]);
  MPI_Waitall(size - 1, sreqs.data(), MPI_STATUSES_IGNORE);
} else {
  MPI_Request req;
  MPI_Isend(&my_sum, 1, MPI_INT, 0, 0, MPI_COMM_WORLD, &req);
  MPI_Wait(&req, &status);
  MPI_Irecv(&global_sum, 1, MPI_INT, 0, 1, MPI_COMM_WORLD, &req);
  MPI_Wait(&req, &status);
}
```

**Complejidad.** Esta implementación lineal centrada en el proceso 0 requiere $2(p-1)$ mensajes, todos pasando por un único proceso: $T(p) = O(p(\alpha+\beta))$. El `MPI_Allreduce` real usa un algoritmo en árbol (reduce + broadcast), con costo $T(p)=O(2\log p(\alpha+\beta))$, como se calculó en la Pregunta 3. La versión punto a punto es asintóticamente peor: crece linealmente con $p$ en vez de logarítmicamente, y el proceso 0 se vuelve un cuello de botella.

**Gather → punto a punto.**

*Versión bloqueada:*

```cpp
if (my_rank == 0) {
  for (int i = 0; i < N; i++) result_array[i] = result_local[i];
  for (int p = 1; p < num_procs; p++)
    MPI_Recv(result_array + p*N, N, MPI_DOUBLE, p, 0, MPI_COMM_WORLD, &status);
} else {
  MPI_Send(result_local, N, MPI_DOUBLE, 0, 0, MPI_COMM_WORLD);
}
```

*Versión no bloqueada:*

```cpp
if (my_rank == 0) {
  for (int i = 0; i < N; i++) result_array[i] = result_local[i];
  std::vector<MPI_Request> reqs(num_procs - 1);
  for (int p = 1; p < num_procs; p++)
    MPI_Irecv(result_array + p*N, N, MPI_DOUBLE, p, 0, MPI_COMM_WORLD, &reqs[p-1]);
  MPI_Waitall(num_procs - 1, reqs.data(), MPI_STATUSES_IGNORE);
} else {
  MPI_Request req;
  MPI_Isend(result_local, N, MPI_DOUBLE, 0, 0, MPI_COMM_WORLD, &req);
  MPI_Wait(&req, &status);
}
```

**Complejidad.** A diferencia de `Allreduce`, `MPI_Gather` no puede combinarse en un árbol porque cada proceso aporta un dato distinto que debe llegar íntegro al raíz: incluso la implementación optimizada de `MPI_Gather` mueve $O(p)$ datos hacia el proceso 0, con costo $T(p)=O(p\alpha + N p\beta)$, del mismo orden que la versión punto a punto. La diferencia práctica entre bloqueado y no bloqueado no está en la complejidad asintótica (ambas son $O(p)$ en el número de mensajes que llegan al root), sino en que la versión no bloqueada permite que las $p-1$ transferencias se solapen en la red (en vez de serializarse una tras otra esperando cada `MPI_Recv`), reduciendo el tiempo real de pared aunque el conteo de mensajes sea el mismo.

**Comparación esperada.** Al medir tiempos, se espera que el `Allreduce`/`Gather` nativos de la biblioteca (implementados con algoritmos afinados, posiblemente en árbol o con solapamiento interno) superen a las versiones punto a punto ingenuas, especialmente al crecer $p$: el caso `Allreduce` punto a punto debería degradarse más notoriamente (lineal vs. logarítmico), mientras que en `Gather` la diferencia entre bloqueado y no bloqueado punto a punto debería ser menor que la ventaja de usar la colectiva optimizada de la biblioteca.

## Pregunta 3 — Desviación estándar (2 pts)

Dada la siguiente función que determina los valores de un array por debajo de la desviación estándar:

```cpp
int calculo(float A[], int n) {
    int i, cont = 0;
    float promedio = 0, suma_cuadrados = 0;
    for (i = 0; i < n; i++)
        promedio += A[i];
    promedio = promedio / n;
    for (i = 0; i < n; i++)
        suma_cuadrados += pow(A[i] - promedio, 2);
    desviacion = suma_cuadrados / (n - 1);
    desviacion = sqrt(desviacion);
    for (i = 0; i < n; i++)
        if (A[i] < desviacion)
            cont++;
    return cont;
}
```

1. Agregue las directivas MPI de comunicación necesarias para paralelizar la función `calculo()`. No necesita generar un código compilable (aunque puede hacerlo). El arreglo `A` está almacenado inicialmente en el maestro, y se retorna un valor que será usado también por el maestro. Considere $n = 2^k$, $p = 2^r$; $k, r \in \mathbb{N}$ (1 pt)
2. Halle una expresión para $T_p(n,p)$, $S(n,p)$, así como el límite del speedup y eficiencia cuando $n$ tiende a infinito. Considere tiempos de comunicación colectiva $O(\log(p)(\alpha+x\beta))$, donde $\alpha$ es el tiempo de latencia, $\beta$ es el tiempo de envío de un byte, y $x$ es el tamaño del mensaje enviado. ¿Considera el algoritmo escalable? Argumente sus respuestas (1 pt)

### Solución

**1) Paralelización con MPI**

```cpp
int calculo(float A[], int n) {
    int i, cont, cont_loc = 0, p;
    float promedio, suma_loc = 0;
    float suma_cuadrados_loc = 0, suma_cuadrados;
    float desviacion;
    float *Aloc;

    MPI_Comm_size(MPI_COMM_WORLD, &p);
    Aloc = (float *)malloc(n / p * sizeof(float));

    // Distribuye A en bloques de n/p elementos
    MPI_Scatter(A, n/p, MPI_FLOAT, Aloc, n/p, MPI_FLOAT, 0, MPI_COMM_WORLD);

    // Suma local, luego promedio global
    for (i = 0; i < n/p; i++) suma_loc += Aloc[i];
    MPI_Allreduce(&suma_loc, &promedio, 1, MPI_FLOAT, MPI_SUM, MPI_COMM_WORLD);
    promedio = promedio / n;

    // Suma de cuadrados local, luego global
    for (i = 0; i < n/p; i++)
        suma_cuadrados_loc += pow(Aloc[i] - promedio, 2);
    MPI_Allreduce(&suma_cuadrados_loc, &suma_cuadrados, 1, MPI_FLOAT, MPI_SUM, MPI_COMM_WORLD);
    desviacion = suma_cuadrados / (n - 1);
    desviacion = sqrt(desviacion);

    // Conteo local de elementos por debajo de la desviación
    for (i = 0; i < n/p; i++)
        if (Aloc[i] < desviacion) cont_loc++;

    // Reduce al maestro
    MPI_Reduce(&cont_loc, &cont, 1, MPI_INT, MPI_SUM, 0, MPI_COMM_WORLD);

    free(Aloc);
    return cont; // válido solo en el proceso 0
}
```

Se usa `MPI_Scatter` para repartir el arreglo $A$ (de tamaño $n$, en el maestro) en bloques de $n/p$ elementos, dos `MPI_Allreduce` para que **todos** los procesos conozcan el promedio y la suma de cuadrados globales (necesarios para calcular `desviacion` localmente en cada proceso antes de contar), y un `MPI_Reduce` final hacia el proceso 0 para acumular el conteo.

**2) Análisis de costo**

*Comunicación.* `Scatter`: el proceso 0 envía un mensaje de $n/p$ elementos a cada uno de los demás procesos:
$$\log p\left(\alpha + \frac{n}{p}\beta\right)$$

`Reduce`: el proceso 0 recibe un mensaje de un elemento de cada proceso y los suma:
$$\log p(\alpha + \beta)$$

`Allreduce` (×2): equivale a un `Reduce` sobre el proceso 0 seguido de un `Broadcast` del resultado:
$$2 \cdot \log p(\alpha + \beta) \quad \text{(por cada Allreduce)}$$

*Cómputo (bucles locales, $n/p$ iteraciones cada uno):*
$$\sum_{i=0}^{n/p-1} 1 + \sum_{i=0}^{n/p-1} 2 + \sum_{i=0}^{n/p-1} 2 = \frac{5n}{p}$$

El tiempo de ejecución paralelo es la suma de comunicación y cómputo:
$$T_p(n,p) = O\!\left(\log p\left(\alpha+\frac{n}{p}\beta\right) + p + \frac{5n}{p}\right)$$

El tiempo secuencial es:
$$T(n) = \sum_{i=0}^{n-1}1 + \sum_{i=0}^{n-1}2 + \sum_{i=0}^{n-1}2 = 5n$$

De donde:
$$S(n,p) = \frac{5n}{\log p\left(\alpha+\frac{n}{p}\beta\right) + p + \frac{5n}{p}} = \frac{1}{\dfrac{1}{p} + \dfrac{\beta\log p}{p} + \dfrac{\log p}{p}}$$

$$\lim_{n\to\infty} S(n,p) = \frac{p}{\beta\log p}$$

$$E(n,p) = \frac{5n/p}{\log p\left(\alpha+\frac{n}{p}\beta\right)+p+\frac{5n}{p}} = \frac{1}{p^2/n + p\log p/n + \log p}$$

**Escalabilidad.** Con $n$ constante (escalabilidad fuerte): $E = O(1/\log p)$, la eficiencia decae al crecer $p$. Para mantener eficiencia constante (escalabilidad débil) se requiere $n \propto p\log p$: el algoritmo **sí es escalable**, siempre que el tamaño del problema crezca al menos proporcionalmente a $p\log p$ junto con el número de procesos.
