## Pregunta 1 — Latencia en Anillo (2 pts)

Mida la latencia en un anillo de $p$ procesos, entendiendo por latencia el tiempo de envío de un mensaje de tamaño 0. Mida tiempos de comunicación con la mayor cantidad de procesos posible. Para medir mejor los tiempos, puede hacer que el mensaje sea pesado (e.g. un array). Realice varios experimentos y promedie resultados. Se recomienda aproximar el tiempo de latencia comparando el tiempo de comunicación de datos de distinto tamaño, de mayor a menor. Promedie varios experimentos, e indique el error en el cálculo de latencia.

**1.1)** Realice el experimento para el caso bloqueado (1 pt)

### Solución

Se mide el tiempo de una vuelta completa del anillo (el rank 0 reenvía y espera de vuelta su propio dato) para dos tamaños de mensaje, y se extrapola $\alpha$ resolviendo el sistema $T(x)=\alpha+x\beta$ con dos puntos:

```cpp
#include <iostream>
#include <vector>
#include <mpi.h>

double ring_time_blocking(int msg_size, int p, int my_rank, int reps = 50) {
  int right = (my_rank + 1) % p;
  int left  = (my_rank - 1 + p) % p;
  std::vector<double> buf(msg_size, 0.0);
  double total = 0.0;

  for (int r = 0; r < reps; r++) {
    MPI_Barrier(MPI_COMM_WORLD);
    double t0 = MPI_Wtime();
    if (my_rank == 0) {
      MPI_Send(buf.data(), msg_size, MPI_DOUBLE, right, 0, MPI_COMM_WORLD);
      MPI_Recv(buf.data(), msg_size, MPI_DOUBLE, left,  0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
    } else {
      MPI_Recv(buf.data(), msg_size, MPI_DOUBLE, left,  0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
      MPI_Send(buf.data(), msg_size, MPI_DOUBLE, right, 0, MPI_COMM_WORLD);
    }
    double t1 = MPI_Wtime();
    if (my_rank == 0) total += (t1 - t0);
  }
  return total / reps;
}

int main(int argc, char** argv) {
  MPI_Init(&argc, &argv);
  int p, my_rank;
  MPI_Comm_size(MPI_COMM_WORLD, &p);
  MPI_Comm_rank(MPI_COMM_WORLD, &my_rank);

  // dos tamaños de mensaje "pesado" para extrapolar alpha por diferencia
  double t_big   = ring_time_blocking(1 << 16, p, my_rank); // n grande
  double t_small = ring_time_blocking(1 << 8,  p, my_rank); // n chico

  if (my_rank == 0) {
    double beta = (t_big - t_small) / ((1<<16) - (1<<8)) / sizeof(double);
    double alpha = t_small - beta * (1<<8) * sizeof(double);
    std::cout << "p=" << p << " alpha (latencia) ~= " << alpha << " s\n";
  }
  MPI_Finalize();
}
```

Nota: el rank 0 mide el tiempo de ida-y-vuelta completa alrededor del anillo (una comunicación bloqueada `Send` a la derecha y `Recv` de la izquierda, con el orden invertido en el resto de procesos para evitar bloqueo mutuo). Repitiendo el experimento y promediando, el **error** en el cálculo de $\alpha$ puede estimarse como la desviación estándar de las $T(x)$ medidas dividida por $\sqrt{\text{reps}}$ (error estándar de la media), propagado a través de la resta usada para extrapolar $\alpha$.

**1.2)** Realice el experimento para el caso no bloqueado (1 pt)

### Solución

```cpp
double ring_time_nonblocking(int msg_size, int p, int my_rank, int reps = 50) {
  int right = (my_rank + 1) % p;
  int left  = (my_rank - 1 + p) % p;
  std::vector<double> sbuf(msg_size, 0.0), rbuf(msg_size, 0.0);
  double total = 0.0;

  for (int r = 0; r < reps; r++) {
    MPI_Barrier(MPI_COMM_WORLD);
    double t0 = MPI_Wtime();
    MPI_Request reqs[2];
    MPI_Isend(sbuf.data(), msg_size, MPI_DOUBLE, right, 0, MPI_COMM_WORLD, &reqs[0]);
    MPI_Irecv(rbuf.data(), msg_size, MPI_DOUBLE, left,  0, MPI_COMM_WORLD, &reqs[1]);
    MPI_Waitall(2, reqs, MPI_STATUSES_IGNORE);
    double t1 = MPI_Wtime();
    if (my_rank == 0) total += (t1 - t0);
  }
  return total / reps;
}
```

Con `MPI_Isend`/`MPI_Irecv` no hace falta invertir el orden entre procesos: todos postulan simultáneamente su envío y su recepción, y el `MPI_Waitall` cierra ambas operaciones. Al repetir el experimento con los mismos dos tamaños de mensaje, se extrapola $\alpha_{nb}$ de la misma forma.

**Comparación.** Se espera $\alpha_{nb} < \alpha_{blocking}$: en el caso bloqueado, la mitad de los procesos del anillo deben esperar a que el vecino complete su `Send` antes de iniciar su propio `Recv` (serialización parcial impuesta por el orden Send/Recv), mientras que en el caso no bloqueado todos los `Isend`/`Irecv` se postulan de inmediato y la red puede procesar las transferencias de forma más concurrente, reduciendo la latencia efectiva medida por vuelta.

## Pregunta 2 — Vectores (2 pts)

El código adjunto (`Ej02_vectores_sec.cpp`) realiza el siguiente cálculo vectorial:
$$C[j] = \sum_{i=0}^{N-1} A[j][i]\cdot B[j][i], \quad j=0,1,\dots,M-1$$

**2.1)** Paralelice el código con MPI, teniendo en cuenta que el proceso $P_0$ obtiene inicialmente los vectores $A$ y $B$, y realiza una distribución por bloques de filas consecutivas (caso 1) y por bloques de columnas (caso 2) sobre todos los procesos. $P_0$ debe obtener el vector resultante. (1 pt)

### Solución

**Caso 1 — bloques de filas.** Cada proceso recibe $M/p$ filas completas (de tamaño $N$ cada una), igual que en el ejercicio de la sesión anterior: cada $C[j]$ depende solo de su propia fila, así que la partición por filas es natural con `MPI_Scatter`.

```cpp
long long M_loc = M / p;
std::vector<double> A_loc(M_loc*N), B_loc(M_loc*N), C_loc(M_loc, 0.0);

MPI_Scatter(A.data(), M_loc*N, MPI_DOUBLE, A_loc.data(), M_loc*N, MPI_DOUBLE, 0, MPI_COMM_WORLD);
MPI_Scatter(B.data(), M_loc*N, MPI_DOUBLE, B_loc.data(), M_loc*N, MPI_DOUBLE, 0, MPI_COMM_WORLD);

for (long long j = 0; j < M_loc; ++j) {
  double acc = 0.0;
  for (long long i = 0; i < N; ++i) acc += A_loc[j*N+i] * B_loc[j*N+i];
  C_loc[j] = acc;
}
MPI_Gather(C_loc.data(), M_loc, MPI_DOUBLE, C.data(), M_loc, MPI_DOUBLE, 0, MPI_COMM_WORLD);
```

**Caso 2 — bloques de columnas.** Ahora cada proceso recibe $N/p$ columnas de **todas** las $M$ filas: cada elemento $C[j]$ pasa a depender de una suma **parcial** repartida entre procesos, por lo que se necesita un `MPI_Reduce` final sobre $C$ en vez de un `Gather`. Como las columnas no son contiguas en memoria (arreglo plano fila-mayor), se usa un tipo derivado `MPI_Type_vector`:

```cpp
long long N_loc = N / p;

MPI_Datatype col_block, col_block_resized;
// M bloques de N_loc elementos, cada bloque separado por un stride de N elementos
MPI_Type_vector(M, N_loc, N, MPI_DOUBLE, &col_block);
// Se redimensiona para que el Scatter avance en unidades de N_loc doubles (columnas)
MPI_Type_create_resized(col_block, 0, N_loc * sizeof(double), &col_block_resized);
MPI_Type_commit(&col_block_resized);

std::vector<double> A_loc(M*N_loc), B_loc(M*N_loc), C_loc(M, 0.0), C_partial(M, 0.0);

MPI_Scatter(A.data(), 1, col_block_resized, A_loc.data(), M*N_loc, MPI_DOUBLE, 0, MPI_COMM_WORLD);
MPI_Scatter(B.data(), 1, col_block_resized, B_loc.data(), M*N_loc, MPI_DOUBLE, 0, MPI_COMM_WORLD);

for (long long j = 0; j < M; ++j) {
  double acc = 0.0;
  for (long long i = 0; i < N_loc; ++i) acc += A_loc[j*N_loc+i] * B_loc[j*N_loc+i];
  C_partial[j] = acc;
}
// Cada C[j] es la suma de las contribuciones parciales de todos los procesos
MPI_Reduce(C_partial.data(), C.data(), M, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);

MPI_Type_free(&col_block_resized);
```

**2.2)** Obtenga el costo computacional y de comunicación para cada uno de los casos anteriores. Utilice un tamaño adecuado para los vectores, y el número de procesos $2,\dots,p$. Grafique $T_{ej}$ vs. $p$ para cada caso y compare los resultados. (1 pt)

### Solución

**Caso 1 (filas).** Comunicación: dos `Scatter` de $MN/p$ elementos y un `Gather` de $M/p$ elementos:
$$T_{comm}^{(1)} = O\!\left(\log p\left(\alpha+\frac{MN}{p}\beta\right)\right)$$
Cómputo: $O(MN/p)$ (idéntico volumen de trabajo que el caso 2).
$$T_p^{(1)}(M,N,p) = O\!\left(\frac{MN}{p}+\log p\left(\alpha+\frac{MN}{p}\beta\right)\right)$$

**Caso 2 (columnas).** Comunicación: dos `Scatter` de $MN/p$ elementos (mismo volumen de datos, pero con tipo derivado no contiguo, lo que en la práctica añade overhead de empaquetado) y un `Reduce` de $M$ elementos (en vez de $M/p$, porque cada proceso aporta una contribución parcial por cada una de las $M$ posiciones, no solo por las que le "pertenecen"):
$$T_{comm}^{(2)} = O\!\left(\log p\left(\alpha+\frac{MN}{p}\beta\right) + \log p(\alpha+M\beta)\right)$$
Cómputo: $O(MN/p)$.
$$T_p^{(2)}(M,N,p) = O\!\left(\frac{MN}{p}+\log p\left(\alpha+\frac{MN}{p}\beta+M\beta\right)\right)$$

**Comparación.** Ambos casos tienen el mismo costo computacional, pero el caso 2 comunica un `Reduce` de tamaño $M$ (independiente de $p$) en vez de un `Gather` de tamaño $M/p$, y además paga el costo de empaquetar/desempaquetar datos no contiguos por el `MPI_Type_vector`. Al graficar $T_{ej}$ vs. $p$ se espera que ambos casos escalen razonablemente bien mientras $MN/p$ domine (cómputo grande), pero que el caso 2 muestre un tiempo base mayor y una caída menos pronunciada al aumentar $p$, ya que el término de comunicación del `Reduce` no decrece con $p$ tan rápido como el `Gather` del caso 1.

## Pregunta 3 — Suavizado (2 pts)

```cpp
int main(int argc, char** argv) {
    long long N = 1LL << 20;
    std::vector<double> global_in(N), global_out(N, 0.0);
    for (long long i = 0; i < N; ++i) global_in[i] = double(i % 101);
    double t_update = 0.0;
    auto t0 = std::chrono::high_resolution_clock::now();
    global_out[0] = (global_in[0] + global_in[0] + global_in[1]) / 3.0;
    for (long long i = 1; i <= N - 2; ++i) {
        global_out[i] = (global_in[i-1] + global_in[i] + global_in[i+1]) / 3.0;
    }
    global_out[N-1] = (global_in[N-2] + global_in[N-1] + global_in[N-1]) / 3.0;
    t_update = std::chrono::duration<double>(t1 - t0).count();
    std::cout << "N=" << N << " t_update(ms): " << t_update << "\n";
    return 0;
}
```

**3.1)** Complete el código con directivas MPI no bloqueadas para que funcione en paralelo. El código no necesita compilar, pero las directivas deben tener todos sus parámetros. (0.5 pts)

### Solución

```cpp
int p, my_rank;
MPI_Comm_size(MPI_COMM_WORLD, &p);
MPI_Comm_rank(MPI_COMM_WORLD, &my_rank);
long long N = 1LL << 20;
long long N_loc = N / p;

std::vector<double> in_loc(N_loc + 2), out_loc(N_loc);
for (long long i = 0; i < N_loc; ++i)
    in_loc[i+1] = double(((my_rank * N_loc) + i) % 101);

int left  = (my_rank == 0)     ? MPI_PROC_NULL : my_rank - 1;
int right = (my_rank == p - 1) ? MPI_PROC_NULL : my_rank + 1;

MPI_Request reqs[4];
MPI_Isend(&in_loc[1],       1, MPI_DOUBLE, left,  0, MPI_COMM_WORLD, &reqs[0]);
MPI_Isend(&in_loc[N_loc],   1, MPI_DOUBLE, right, 1, MPI_COMM_WORLD, &reqs[1]);
MPI_Irecv(&in_loc[0],       1, MPI_DOUBLE, left,  1, MPI_COMM_WORLD, &reqs[2]);
MPI_Irecv(&in_loc[N_loc+1], 1, MPI_DOUBLE, right, 0, MPI_COMM_WORLD, &reqs[3]);

if (my_rank == 0)     in_loc[0]       = in_loc[1];
if (my_rank == p - 1) in_loc[N_loc+1] = in_loc[N_loc];

for (long long i = 2; i <= N_loc - 1; ++i)
    out_loc[i-1] = (in_loc[i-1] + in_loc[i] + in_loc[i+1]) / 3.0;

MPI_Waitall(4, reqs, MPI_STATUSES_IGNORE);
out_loc[0]       = (in_loc[0]       + in_loc[1]    + in_loc[2])       / 3.0;
out_loc[N_loc-1] = (in_loc[N_loc-1] + in_loc[N_loc] + in_loc[N_loc+1]) / 3.0;
```

**3.2)** Determine la complejidad del algoritmo considerando cómputo y comunicación (1 pt)

### Solución

Cómputo: $O(N/p)$ (tres operaciones por elemento local). Comunicación: solo dos valores escalares intercambiados con los vecinos, sin colectivas: $O(\alpha)$.
$$T_p(N,p) = O\!\left(\frac{N}{p}+\alpha\right)$$

**3.3)** Discuta sobre la ventaja del no bloqueo vs. bloqueo en el código desarrollado (0.5 pts)

### Solución

En este problema, cada proceso necesita solo un valor de cada vecino (el halo) para calcular sus dos elementos de borde, pero puede calcular todos sus elementos internos ($N/p - 2$ de ellos) sin depender de ningún dato externo. Con comunicación **bloqueada**, el proceso tendría que esperar a que `Send`/`Recv` completen antes de poder hacer cualquier cómputo, desperdiciando ese tiempo de espera. Con comunicación **no bloqueada** (`MPI_Isend`/`MPI_Irecv`), el intercambio de halos se lanza de inmediato y el proceso puede calcular en paralelo todos los elementos internos mientras la red transfiere los 2 valores de borde; solo al llegar a los bordes locales se necesita `MPI_Wait`(all) para garantizar que el halo ya llegó. Esto **solapa comunicación con cómputo**, ocultando casi por completo la latencia de red detrás del trabajo útil, lo cual es especialmente valioso aquí porque el volumen de datos comunicado (2 escalares) es mínimo frente al volumen de cómputo local ($O(N/p)$), maximizando el beneficio relativo del solapamiento.
