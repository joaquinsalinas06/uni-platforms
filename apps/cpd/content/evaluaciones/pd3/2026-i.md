## Pregunta 1 — Comunicación cíclica (2.5 pts)

Desarrolle un código C++-MPI que propague el rank desde cada proceso al resto de procesos en comunicación cíclica, y además realice la suma acumulada, según los siguientes pasos (en cada proceso):

1. Almacena el valor de `rank` en `snd_buff`
2. Envía `snd_buff` a su vecino derecho
3. Recibe `rcv_buff` de su vecino izquierdo
4. Prepara el `snd_buff` para la siguiente iteración
5. Acumula los `rank`'s en una variable

Es decir, en el caso de $p=3$, el rank=0 se envía desde el maestro a los procesos 1 y 2, el rank=1 se envía a los procesos 2 y 0, y el rank=2 a los procesos 0 y 1. Los ranks recibidos deben sumarse en cada proceso. En el ejemplo, cada proceso obtendrá la suma de 3.

Desarrolle lo siguiente:

**a)** Utilice comunicación bloqueada con send sincrónico (`MPI_Ssend`) para resolver el problema. Describa el procedimiento según lo visto en clase (1 pt). Código adjunto: `Ejercicio01_Ssend.cpp`

### Solución

El código adjunto propone (a propósito, con error) la siguiente implementación:

```cpp
right = (my_rank+1)      % size;
left  = (my_rank-1+size) % size;

sum = 0;
snd_buf = my_rank;
for (i = 0; i < size; i++) {
  if (my_rank == 0) {
    MPI_Recv(&rcv_buf, 1, MPI_INT, left,  17, MPI_COMM_WORLD, &status);
    MPI_Ssend(&snd_buf, 1, MPI_INT, right, 17, MPI_COMM_WORLD);
  } else {
    MPI_Ssend(&snd_buf, 1, MPI_INT, right, 17, MPI_COMM_WORLD);
    MPI_Recv(&rcv_buf, 1, MPI_INT, left,  17, MPI_COMM_WORLD, &status);
  }
  snd_buf = rcv_buf;
  sum += rcv_buf;
}
```

El propio código señala el problema: para $p>1$, el proceso 0 hace `Recv`-antes-que-`Ssend` y el resto hace `Ssend`-antes-que-`Recv`, lo cual rompe el ciclo de bloqueo mutuo entre el rank 0 y sus vecinos — **pero solo de forma serializada**: el rank 0 debe esperar a que su vecino izquierdo (el último rank) le envíe antes de poder enviar el suyo, lo que fuerza a que las $p$ transferencias del anillo se ejecuten una detrás de otra en vez de en paralelo (cada `Ssend` no se completa hasta que el receptor llama a `Recv`, y solo hay una "puerta de entrada" desestabilizada en el rank 0). Además, con $p=1$ el programa se bloquea siempre, porque el único proceso intentaría hacer `Ssend` y `Recv` consigo mismo sin que ninguna de las dos directivas tenga con quién emparejarse primero.

El procedimiento correcto, visto en clase, rompe el ciclo de forma simétrica: la mitad de los procesos (por ejemplo, los de rank par) invierten el orden Recv/Send respecto a la otra mitad, o bien se usa comunicación no bloqueada en al menos un extremo de cada intercambio, de modo que ningún proceso quede esperando indefinidamente dentro de una llamada bloqueante mientras todos los demás hacen lo mismo.

**b)** Utilice comunicación bloqueada con send buffered (`MPI_Bsend`) para resolver el problema. Consulte la forma correcta de usar `MPI_Bsend`, ya que necesita reservar y liberar el buffer con `MPI_Buffer_attach`, `MPI_Buffer_detach`. Describa el procedimiento según lo visto en clase (1 pt). Código adjunto: `Ejercicio01_Bsend.cpp`

### Solución

```cpp
right = (my_rank+1)      % size;
left  = (my_rank-1+size) % size;
int bsize = sizeof(int) + MPI_BSEND_OVERHEAD;
void* buffer = std::malloc(bsize);
MPI_Buffer_attach(buffer, bsize);

sum = 0;
snd_buf = my_rank;
for (i = 0; i < size; i++) {
  if (my_rank == 0) {
    MPI_Recv(&rcv_buf, 1, MPI_INT, left,  17, MPI_COMM_WORLD, &status);
    MPI_Bsend(&snd_buf, 1, MPI_INT, right, 17, MPI_COMM_WORLD);
  } else {
    MPI_Bsend(&snd_buf, 1, MPI_INT, right, 17, MPI_COMM_WORLD);
    MPI_Recv(&rcv_buf, 1, MPI_INT, left,  17, MPI_COMM_WORLD, &status);
  }
  snd_buf = rcv_buf;
  sum += rcv_buf;
}

void* detached_buffer;
int detached_size;
MPI_Buffer_detach(&detached_buffer, &detached_size);
std::free(detached_buffer);
```

Aquí se reserva explícitamente un búfer con `MPI_Buffer_attach` (tamaño de un `int` más el overhead `MPI_BSEND_OVERHEAD` que exige la implementación) antes de usar `MPI_Bsend`, y se libera con `MPI_Buffer_detach` al final — `MPI_Buffer_detach` además bloquea hasta que todos los envíos buffered pendientes hayan sido efectivamente transmitidos, garantizando que el búfer no se libere mientras aún hay datos por enviar. A diferencia de `MPI_Ssend`, `MPI_Bsend` copia el mensaje al búfer y retorna de inmediato sin esperar a que el receptor llame a `Recv`, por lo que en teoría **desbloquea** el envío. Sin embargo, el código adjunto conserva la misma estructura serializada (Recv-antes-que-Send en el rank 0, Send-antes-que-Recv en el resto) heredada del ejercicio (a): aunque el `Bsend` en sí no bloquea, el `Recv` posterior de cada proceso sigue esperando secuencialmente a su vecino izquierdo, de modo que el paralelismo real ganado es parcial, y solo se manifiesta si el tamaño del mensaje cabe cómodamente en el búfer reservado.

**c)** Analice el paralelismo de ambas implementaciones según lo discutido en clase. (0.5 pt)

### Solución

El caso sincrónico (`Ssend`) siempre se serializa/bloquea: cada envío exige que el receptor ya esté en su `Recv`, por lo que el anillo se recorre en cascada, un proceso a la vez. El caso buffered (`Bsend`) se desbloquea **parcialmente**: el `Send` ya no espera al receptor, pero solo si el tamaño del mensaje es pequeño (cabe en el búfer reservado); si el mensaje fuera más grande que el búfer, `Bsend` fallaría o se degradaría, perdiendo la ventaja de desbloqueo.

## Pregunta 2 — Métricas (2 pts)

El algoritmo de Prim tiene una complejidad
$$T(n,p) = O\left(\frac{n^2}{p} + n\log(p)\right)$$

**a)** Determine el speedup y eficiencia (dado $T_s = O(n^2)$) (0.5 pt)

### Solución

Ya que $T_s = O(n^2)$,
$$S = O\!\left(\frac{n^2}{\dfrac{n^2}{p}+n\log p}\right)$$
$$E = O\!\left(\frac{1}{1+\dfrac{p\log p}{n}}\right)$$

**b)** ¿Cómo depende el número de procesos $p$ de la cantidad de elementos $n$, si el speedup tiene una complejidad constante? (0.5 pt)

### Solución

Si $S=O(1)$, entonces $n^2 \propto \dfrac{n^2}{p}+n\log p$. Analizando ambos términos, solo el segundo brinda una relación entre $n$ y $p$, por lo tanto $n \propto \log p$.

**c)** ¿Considera que este último caso representa un algoritmo escalable? (0.5 pt)

### Solución

En este caso $E = O\!\left(\dfrac{1}{1+p}\right)$, por lo que $E$ cae con $p$. No es escalable.

**d)** ¿Bajo qué condición es el caso (a) escalable? (0.5 pt)

### Solución

Para $E=O(1)$, $n=O(p\log p)$.

## Pregunta 3 — Suavizado (2.5 pts)

El problema del suavizado de una imagen de $n \times n$ píxeles consiste en suavizar el valor de la intensidad ($U_{i,j}$) de cada píxel ($0 \le i,j < n$) calculando el promedio de los valores de intensidad de los píxeles vecinos, en dos dimensiones.
$$U_{i,j} = \frac{U_{i-1,j}+U_{i+1,j}+U_{i,j+1}+U_{i,j-1}}{4}$$

**a)** Desarrolle un algoritmo en paralelo bajo el paradigma de memoria distribuida usando como base el formalismo PRAM (pardo) para el problema del suavizado. Note que debe agregar directivas de comunicación, como `MPI_Send()`, `MPI_Recv()`, `MPI_Scatter()`, etc. (1 pt)

### Solución

**Entrada:** Matriz $U[n][m]$, procesos $P[r][s]$, con $n=2^k$, $m=2^l$, $r=2^t$, $s=2^u$; $k,l,t,u \in \mathbb{Z}$.
**Salida:** Matriz $U[n][m]$ con celdas suavizadas.

```
scatter(U, (n·m)/p)

if (P00) send(n/p, P01), send(m/p, P10)
else if (P_{p-1,p-1}) recv(n/p, P_{p-1,p-2}), recv(m/p, P_{p-2,p-1})
else {
  send(n/p, P_{s,r+1}), send(m/p, P_{s+1,r}), send(n/p, P_{s,r-1}), send(m/p, P_{s-1,r})
  recv(n/p, P_{s,r+1}), recv(m/p, P_{s+1,r}), recv(n/p, P_{s,r-1}), recv(m/p, P_{s-1,r})
}

for i ∈ {1,...,n}, j ∈ {1,...,m} pardo
    U[i,j] = (U[i-1,j] + U[i+1,j] + U[i,j-1] + U[i,j+1]) / 4

gather(U, (n·m)/p)
```

Se reparte la matriz con `scatter` en bloques de $(n\cdot m)/p$ celdas entre los procesos $P[r][s]$, dispuestos en una malla 2D. Cada proceso intercambia las filas/columnas de borde (halos) con sus vecinos en la malla usando `send`/`recv` de comunicación punto a punto (los procesos en las esquinas de la malla solo tienen vecinos en un lado, por eso los casos especiales para $P_{00}$ y $P_{p-1,p-1}$). El bucle `pardo` (formalismo PRAM) representa el cómputo local en paralelo sobre las celdas ya disponibles (locales + halos recibidos). Finalmente se recolecta el resultado con `gather`.

**b)** Calcule la eficiencia del modelo. ¿Es escalable? (1 pt)

### Solución

Para memoria distribuida:
$$T(n,p) = O\!\left(\frac{n^2}{p}+1\right) + T_{Scatter} + T_{Gather} + T_{Send/Recv} = O\!\left(\frac{n^2}{p} + \log p\left(\alpha+\frac{n}{p}\beta\right) + p(\alpha+\beta)\right)$$

$$S = O\!\left(\frac{n^2}{\dfrac{n^2}{p}+\dfrac{n\log p}{p}+\log p+p}\right)$$

$$E = O\!\left(\frac{n^2/p}{\dfrac{n^2}{p}+\dfrac{n\log p}{p}+\log p+p}\right) = O\!\left(\frac{1}{1+\log p/n+p\log p/n^2+p^2/n^2}\right)$$

Teóricamente, el modelo distribuido es escalable bajo la condición $n \propto p$.

**c)** ¿En qué casos considera recomendable resolver este problema en un procesador de memoria compartida, o en una arquitectura distribuida? Argumente su respuesta. (0.5 pts)

### Solución

La elección entre memoria compartida o distribuida dependerá directamente del tamaño del problema y la capacidad por procesador (memoria). Modelos realistas de suavizado (o problemas similares) deberán ser distribuidos por la cantidad de puntos: si la imagen (o malla) cabe cómodamente en la memoria de un solo nodo y el número de procesos es moderado, memoria compartida evita el overhead de comunicación explícita ($\alpha,\beta$) y aprovecha mejor la localidad de los halos; si el problema es demasiado grande para la memoria de un solo nodo, o se requiere escalar a muchos más procesos de los que un nodo puede ofrecer, la arquitectura distribuida (memoria distribuida + MPI) es la única opción viable, a pesar del costo adicional de comunicación entre vecinos.
