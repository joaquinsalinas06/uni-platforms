## 1. Idea

Cada versión nace de un fallo de la anterior. Aquí están las FSM de las slides, con el emisor y el receptor de cada una (usa los puntos de cada figura para cambiar de lado).

El problema que deja abierto (slide): **el ACK o NAK también puede corromperse**. Añadir más bits de checksum sirve para paquetes corruptos, no para perdidos; reenviar un ACK/NAK corrupto introduce **duplicados**, y el receptor no puede saber a priori si un paquete es nuevo o una retransmisión.

## 3. Ejemplo resuelto

**Ejercicios 3, pregunta 1 (también Ejercicios 2, pregunta 5): el receptor de la Figura 1, con el emisor de la Figura 2, se puede bloquear.**

La diferencia con rdt2.1: en la Figura 1, un paquete duplicado (por ejemplo, un `has_seq0` mientras se espera el 1) provoca un **NAK** en lugar de un ACK.

Ese es el estado de **bloqueo** que pide mostrar el ejercicio. La corrección de rdt2.1 es que, ante un duplicado, el receptor responda **ACK** (no NAK): así el emisor avanza.

## 4. Errores típicos

- Confundir "esperar 0 de abajo" (qué número espera el receptor) con "esperar llamada 0 de arriba" (el emisor, listo para enviar datos).
- En rdt2.1, responder NAK a un duplicado correcto.
- En rdt2.2, olvidar que el ACK ahora **lleva** un número.
