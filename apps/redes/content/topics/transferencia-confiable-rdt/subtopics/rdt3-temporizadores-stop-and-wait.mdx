## 1. Idea

Si el canal también puede **perder** paquetes o ACK, el emisor necesita saber cuándo desistir de esperar. rdt3.0 agrega un **temporizador**: si vence antes de recibir el ACK, retransmite. La secuencia 0, 1, 0, 1… lo hace el *alternating-bit protocol*.

---

- Al enviar se arranca el temporizador; al recibir el ACK correcto se detiene.
- `timeout`: retransmite y rearranca el temporizador.
- Los paquetes corruptos o con ACK del otro número se ignoran (Λ).
- Mientras espera un ACK el emisor sigue sin aceptar datos de arriba: sigue siendo **stop-and-wait**.

El receptor de las slides para rdt3.0 no se dibuja aparte; las trazas siguientes son consistentes con el receptor de rdt2.2 (reconoce duplicados y reenvía ACK).

### Por qué stop-and-wait rinde poco

Ejemplo de la slide: enlace de $R = 1\text{ Gbps}$, paquetes de $L = 8000$ bits (1000 bytes) y $\text{RTT} \approx 30\text{ ms}$.

$$d_{\text{trans}} = \frac{L}{R} = \frac{8000}{10^9}\text{ s} = 8\ \mu\text{s} = 0{,}008\text{ ms}$$

## 3. Ejemplo resuelto

Ejercicio extra (Ejercicios Extra, pregunta 3): transferir un archivo de 2 MB entre dos laptops sobre UDP con 15 % de pérdidas artificiales, implementando rdt3.0:

- Emisor: parte el archivo en trozos de 1024 bytes, les pone número de secuencia 0 o 1 y espera el ACK; si hay timeout (p. ej. 0,5 s) retransmite el trozo actual.
- Receptor: si llega el trozo esperado, lo escribe y envía el ACK correspondiente; si es un duplicado, descarta los datos pero **reenvía el ACK** (el anterior seguramente se perdió).

Comparación de `md5sum` en ambos extremos para comprobar que el archivo es idéntico. El código está en [Laboratorio UDP y RDT](/topics/lab-udp-rdt-simulacion).

## 4. Errores típicos

- Poner el temporizador **menor que el RTT**: provoca el caso (d), con duplicados innecesarios.
- No reenviar el ACK de un duplicado: si el ACK se perdió, el emisor se queda esperando.
- Pensar que el temporizador evita las pérdidas: solo las repara retransmitiendo.
