## 1. Abre una captura y olvida las siglas durante un momento

Wireshark te muestra muchos paquetes con números, pero el problema de clase es muy concreto: **¿qué envió el cliente, qué recibió el servidor y cómo lo confirmó?**

Una **trama** es una unidad capturada en la interfaz de red. Dentro puede haber un **segmento TCP**, que transporta una porción de datos de la aplicación. El mismo archivo HTTP puede ocupar varios segmentos.

**Seq** significa *sequence number*, número de secuencia: identifica el **primer byte** de datos del segmento. **Len** es la cantidad de bytes de carga TCP. **Ack** significa confirmación: indica el **siguiente byte que el receptor espera en orden**.

Si un segmento tiene **Seq=1** y **Len=1448 B**, sus datos van desde el byte 1 hasta el 1448. Un posterior **Ack=1449** quiere decir «recibí hasta 1448», **no** «ya recibí el 1449».

## 2. Seguir el primer mensaje de la captura oficial

Antes de los datos, TCP abre la conexión con tres mensajes llamados **handshake**: **SYN → SYN/ACK → ACK**. Las tramas oficiales **1, 2 y 3** muestran ese intercambio. El SYN consume un número de secuencia, razón por la que la primera carga del cliente empieza en **Seq relativo=1**.

En la **trama 4** el cliente manda el comienzo del HTTP POST con **Seq=1 y Len=1448**. La **trama 7** del servidor anuncia **Ack=1449**. Esa es la confirmación esperada.

La siguiente carga de 1448 B empieza en **Seq=1449** y el ACK posterior avanza a **2897**. No es necesario memorizar 2897: **1449+1448=2897**.

A partir de aquí, cuando un ACK salta varios bloques, recuerda que TCP confirma **acumulativamente**: un solo Ack puede confirmar varios segmentos consecutivos. La tabla del laboratorio utiliza esa propiedad para emparejar datos y confirmaciones.

## 4. Errores típicos

- Interpretar `Ack=1449` como “recibió el byte 1449”: espera ese byte; confirmó hasta 1448.
- Atribuir todos los bytes TCP a alice.txt, olvidando HTTP.
