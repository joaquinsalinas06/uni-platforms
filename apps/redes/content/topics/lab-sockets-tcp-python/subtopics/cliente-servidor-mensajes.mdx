## 1. Dos programas que se hablan: qué hace cada uno

En este laboratorio no estamos programando Internet entero. Vamos a crear **dos programas** que se comunican mediante TCP.

El **servidor** es el que prepara un puerto y espera. El **cliente** es el que conoce la dirección y el puerto del servidor y pide abrir la conexión. Un **puerto** es un número usado para identificar el servicio o proceso que recibirá la comunicación.

El servidor usa **socket()** para crear su extremo, **bind()** para asociarlo a una dirección y puerto, **listen()** para quedar preparado, y **accept()** para recibir una conexión. El cliente utiliza **connect()**. El sistema operativo realiza los tres mensajes de apertura TCP —**SYN, SYN/ACK, ACK**— mientras esos programas cooperan; no los dibujamos ni los enviamos manualmente desde Python.

## 2. La dificultad real: TCP no separa los mensajes por ti

Supón que el cliente llama a send para transmitir «Hola» y después «Mundo». El receptor no tiene garantizado que su primera llamada a **recv()** entregue exactamente «Hola». TCP entrega una **secuencia ordenada de bytes**, y cada recv puede devolver menos datos de los pedidos o reunir bytes de varios envíos.

Por eso el programa necesita una regla propia: **antes de cada mensaje, enviar cuatro bytes que indican su longitud**. Si el mensaje tiene 5 bytes, el receptor primero lee cuatro bytes, descubre el número 5 y después sigue leyendo hasta completar esos **cinco**. La función **recv_exact** repite recv hasta lograrlo. Si la conexión se cierra antes de tiempo, se informa que el mensaje está incompleto.

**sendall()** intenta completar el envío de los bytes indicados o devuelve error. Tampoco significa «crea exactamente un segmento TCP». Los segmentos son una decisión del transporte, mientras que el tamaño del mensaje pertenece a nuestra aplicación.

El servidor recibe cada mensaje, espera **dos segundos** y después envía el texto «ACK aplicacion». Ese texto **no es un ACK TCP**. Los ACK TCP los genera automáticamente la pila del sistema para confirmar bytes; por eso pueden verse en Wireshark antes de que el programa termine de esperar sus dos segundos.

**¿Qué mide el cliente?** Inicia un cronómetro antes del mensaje y lo detiene tras la respuesta de aplicación: ese **RTT de aplicación** incluye la pausa artificial. Luego espera **un segundo** antes de enviar el siguiente mensaje. No debes sumar ese segundo al RTT de cada intercambio si el cronómetro comienza después de él.

### El código importante, con la regla de longitud visible


```python
def recv_exact(conn, count):
    data = bytearray()
    while len(data) < count:
        chunk = conn.recv(count - len(data))
        if not chunk:
            raise EOFError('Conexión cerrada antes de completar el mensaje')
        data.extend(chunk)
    return bytes(data)


def send_message(conn, data):
    if len(data) > MAX_MESSAGE:
        raise ValueError('Mensaje mayor que 1 MiB')
    conn.sendall(struct.pack('!I', len(data)) + data)


def receive_message(conn):
    size = struct.unpack('!I', recv_exact(conn, 4))[0]
    if size > MAX_MESSAGE:
        raise ValueError('Longitud de mensaje mayor que 1 MiB')
    return recv_exact(conn, size)
```


## 3. Ejemplo resuelto

El cliente envía tres mensajes secuenciales. El servidor espera 2 s antes de cada respuesta; el cliente espera 1 s después de cada respuesta antes del siguiente envío. El reloj usa `perf_counter` y mide desde antes de enviar hasta recibir la respuesta completa. No se resta el segundo entre intercambios: ese segundo queda fuera de cada medición.

En Wireshark, compara el RTT de aplicación con `tcp.analysis.ack_rtt`. El primero incluye espera y procesamiento de Python; el ACK de transporte puede llegar mucho antes. Es la pila del sistema, no Wireshark, la que envía ese ACK.

## 4. Errores típicos

- Medir desde antes de `connect` y atribuir el handshake a cada mensaje.
- Interpretar PSH como separador fiable de mensajes.
- Afirmar que Ctrl+C siempre produce RST: el resultado depende del cierre, datos pendientes y sistema; hay que capturarlo.
