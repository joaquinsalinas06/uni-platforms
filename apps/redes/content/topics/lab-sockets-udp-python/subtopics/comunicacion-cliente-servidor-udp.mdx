## 1. Idea

El servidor se asocia a un puerto fijo; el cliente no hace `bind` y el sistema operativo le asigna un puerto temporal. Con eso se ve en Wireshark cómo los puertos se invierten entre pregunta y respuesta.

---

## 2. Conceptos

### Servidor y cliente de los Ejercicios 2 (pregunta 8)

```python
# udp_server.py
import socket
sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
sock.bind(("0.0.0.0", 9999))
print("UDP server listening on port 9999...")
while True:
    data, addr = sock.recvfrom(1024)
    print(f"Received from {addr}: {data.decode()}")
    sock.sendto(b"ACK", addr)
```

```python
# udp_client.py
import socket
sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
for i in range(3):
    msg = f"Message {i+1}".encode()
    sock.sendto(msg, ("127.0.0.1", 9999))
    data, _ = sock.recvfrom(1024)
    print(f"Server reply: {data.decode()}")
```

### Qué observar (preguntas de los checkpoints)

- Puerto del servidor: fijo (9999). Puerto del cliente: temporal.
- La respuesta del servidor va al puerto del cliente (el que muestra `addr`).
- Dos servidores en el mismo puerto UDP: el segundo falla al hacer `bind` *(derivado)*.
- Cliente enviando con el servidor apagado: el cliente se queda esperando en `recvfrom` *(derivado)*; el aviso, si aparece, es un ICMP *Port Unreachable* (pregunta 11 del ejercicio).
- Mensajes más grandes: el lab propone 12 000 bytes; el límite teórico se discute en [Ventajas y segmento UDP](/topics/protocolo-udp/ventajas-y-segmento-udp).

## 3. Ejemplo resuelto

Las capturas esperadas del loopback: un paquete UDP de ida y otro de vuelta por mensaje. En el de ida $(\text{origen}, \text{destino}) = (\text{temporal}, 9999)$; en el de vuelta $(9999, \text{temporal})$.

---

## 4. Errores típicos

- Esperar que el cliente tenga el mismo puerto en cada ejecución: es temporal.
- Responder a un puerto fijo en vez de a `addr`.
- Confundir el "ACK" del programa con un acuse de UDP: el protocolo no confirma nada.
