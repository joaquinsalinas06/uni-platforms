### Pregunta 1: DNS y descarga de un archivo (2 pt)

<ExamStatement>

**(2 pt)** Un cliente accede por primera vez a un sitio web cuyo nombre de dominio no está en caché. Debe consultar **tres servidores DNS** secuencialmente ($RTT_1, RTT_2, RTT_3$) antes de establecer conexión con el servidor web ($RTT_s$).

El archivo principal es un video corto de tamaño significativo (no despreciable), por lo que **el tiempo de transmisión debe considerarse**. El enlace cliente-servidor tiene una tasa de transmisión de $R$ bps y el tamaño del archivo es $S$ bits.

a) Exprese el tiempo total hasta recibir completamente el archivo, considerando tanto la resolución DNS como la descarga.

b) Si $RTT_1 = 60$ ms, $RTT_2 = 80$ ms, $RTT_3 = 100$ ms, $RTT_s = 70$ ms, $S = 8$ MB, y $R = 4$ Mbps, calcule el tiempo total aproximado de descarga.

c) Analice qué parte del proceso domina la latencia total y cómo podría optimizarse.

</ExamStatement>

**Solución.**

**a) Tiempo total.** DNS son tres RTT sumados; luego handshake TCP ($\text{RTT}_s$), el GET con su respuesta ($\text{RTT}_s$) y la transmisión del archivo:

$$T = \text{RTT}_1 + \text{RTT}_2 + \text{RTT}_3 + 2\,\text{RTT}_s + \frac{S}{R}$$

**b) Datos.** $\text{RTT}_1 = 60$ ms, $\text{RTT}_2 = 80$ ms, $\text{RTT}_3 = 100$ ms, $\text{RTT}_s = 70$ ms, $S = 8$ MB, $R = 4$ Mbps.

- Conversión (1 MB = 8 Mb): $S = 64$ Mb, así que $S/R = 64/4 = 16$ s.
- DNS: $60 + 80 + 100 = 240$ ms. Web: $2 \times 70 = 140$ ms.

$$T = 0{,}240 + 0{,}140 + 16 = \boxed{16{,}38\text{ s}}$$

*(Con $1\text{ MB} = 2^{20}$ bytes, $S/R \approx 16{,}78$ s: por eso el enunciado pide un tiempo "aproximado".)*

### Pregunta 2: Distribución cliente-servidor frente a P2P (2 pt)

<ExamStatement>

**(2.0 pt)** Considere un archivo de tamaño $F$ y $N$ peers. Un servidor con velocidad de subida $u_s$ intenta transmitir el archivo hacia los $N$ peers, cada uno con su velocidad de descarga $d_n$ y velocidad de subida $u_n$. Además $d_{min} = \min\{d_1, d_2, \dots, d_N\}$ es la velocidad de descarga mínima entre los peers. Explique cómo se obtienen las siguientes expresiones del tiempo de distribución total para las arquitecturas cliente-servidor y P2P e indique las implicancias cuando el número de peers es muy alto

$$D_{CS} \ge \max\left\{\frac{NF}{u_s}, \frac{F}{d_{\min}}\right\} \qquad D_{P2P} \ge \max\left\{\frac{F}{u_s}, \frac{F}{d_{\min}}, \frac{NF}{u_s + \sum_{i=1}^{N} u_i}\right\}$$

</ExamStatement>

**Solución.**

Archivo de $F$ bits, $N$ pares, servidor con subida $u_s$, par $i$ con bajada $d_i$ y subida $u_i$, $d_{\min} = \min\{d_1, \dots, d_N\}$. Se piden las dos cotas del enunciado:

$$D_{cs} \ge \max\left\{\frac{NF}{u_s},\ \frac{F}{d_{\min}}\right\} \qquad D_{P2P} \ge \max\left\{\frac{F}{u_s},\ \frac{F}{d_{\min}},\ \frac{NF}{u_s + \sum_{i=1}^{N} u_i}\right\}$$

**Cliente-servidor.** El servidor envía $N$ copias de forma secuencial: una copia tarda $F/u_s$, las $N$ copias $NF/u_s$. Cada cliente baja una copia; el más lento tarda $F/d_{\min}$. Ambas cotas se cumplen a la vez, y el tiempo es el máximo.

**P2P.** El servidor debe subir al menos una copia ($F/u_s$); el cliente más lento tarda $F/d_{\min}$; y entre todos hay que bajar $NF$ bits, con capacidad máxima de subida $u_{\text{total}} = u_s + u_1 + \dots + u_N$, de donde $NF/u_{\text{total}}$.

**Implicancias con $N$ muy grande.** En cliente-servidor $NF/u_s$ crece **linealmente** con $N$. En P2P, con pares de subida parecida $u$, $\frac{NF}{u_s + Nu} \to \frac{F}{u}$ *(derivado)*: el tiempo se estabiliza, porque cada par que llega también aporta subida. Gráfica y detalle: [escalabilidad](/topics/arquitecturas-p2p-distribucion/analisis-escalabilidad-asintotica).

**Cómo funciona (rdt2.1, receptor).** Dos estados: *Esperar 0 de abajo* y *Esperar 1 de abajo*. En *Esperar 0*:

- Paquete **corrupto**: responde NAK y se queda.
- Paquete correcto con número **0**: lo entrega a la capa superior, responde ACK y pasa a *Esperar 1*.
- Paquete correcto con número **1**: es un **duplicado** (el emisor no recibió el ACK anterior). No se entrega otra vez, pero se **reenvía el ACK** y se queda en el mismo estado.

En *Esperar 1* es simétrico.

**¿Lida con duplicados?** Sí: el número de secuencia (0 o 1) permite distinguir un dato nuevo de una retransmisión; el duplicado se descarta y se vuelve a confirmar.

**Cambio para pasar a rdt2.2.** Se elimina el NAK: el ACK ahora **lleva el número de secuencia** del último paquete recibido bien. Ante un paquete corrupto o un duplicado, el receptor responde con el ACK del último paquete correcto (en *Esperar 0*: `ACK 1`; en *Esperar 1*: `ACK 0`). El emisor trata un ACK con el número equivocado como un NAK y retransmite.

### Pregunta 4: protocolo solo con NAK (3 pt)

<ExamStatement>

**(3.0 pt)** Considere un modelo que admite errores en los bits y pérdida de paquetes. Dado un protocolo de transferencia de datos confiable que usa solo *negative acknowledgments* (NAKs):

a) ¿Cómo se daría cuenta el sistema de que ocurrió un error o una pérdida?

b) Suponga que el emisor envía datos solo con poca frecuencia. ¿Sería preferible un protocolo que use solo NAKs en lugar de uno que use ACKs? Justifique.

</ExamStatement>

**Solución.**

**a) ¿Cómo se entera de un error o una pérdida?**

- *Error de bits:* el receptor detecta el paquete corrupto con el checksum y envía NAK.
- *Pérdida:* el receptor no ve nada. Solo se entera cuando llega un paquete **posterior** y nota un hueco en los números de secuencia (hacen falta números crecientes; con 0 y 1 no alcanza). Si lo que se pierde es el último paquete, nunca llega uno posterior: la pérdida no se detecta.

**b) Emisor con poca frecuencia: ¿NAK o ACK?** Es preferible el protocolo con **ACK**. Con envíos espaciados, un hueco no se descubre hasta el siguiente paquete, que puede tardar mucho. Con ACK y temporizador (rdt3.0), el emisor retransmite poco después de la pérdida.

</ExamStatement>

**Solución.**

Sí. Un servidor DNS guarda en su caché cada nombre que resuelve y esa entrada desaparece pasado su TTL. Si se pueden consultar las cachés de los DNS locales del departamento, se listan los nombres externos presentes y se repite la consulta a lo largo del día: los sitios que aparecen una y otra vez (o cuyo registro se renueva apenas expira) los están pidiendo muchos usuarios.
