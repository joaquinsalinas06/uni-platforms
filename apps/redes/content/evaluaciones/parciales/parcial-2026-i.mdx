## Pregunta 1: Protocolos de aplicación y HTTP (2 puntos)

<ExamStatement>

Un usuario desea descargar una página HTML que contiene 3 imágenes pequeñas. El nombre de dominio no está en caché y requiere consultar dos servidores DNS de forma iterativa ($RTT_1$ y $RTT_2$). Una vez obtenida la IP, se accede al servidor web ($RTT_s$). El archivo HTML base tiene un tamaño despreciable, pero cada una de las 3 imágenes tiene un tamaño de $S$ bits. La tasa de transmisión del enlace es $R$ bps.

a) **Caso A (HTTP No Persistente):** Exprese el tiempo total desde que el usuario hace clic hasta que se reciben las 3 imágenes. Asuma que las conexiones TCP para las imágenes se realizan de forma secuencial. *(1 pt)*

b) **Caso B (HTTP Persistente sin pipelining):** Exprese el tiempo total para el mismo proceso. *(0.5 pt)*

c) **Cálculo Numérico:** Si $RTT_1 = 50$ ms, $RTT_2 = 70$ ms, $RTT_s = 100$ ms, $S = 2$ Mbits (cada imagen) y $R = 10$ Mbps, calcule el tiempo total para el **Caso B**. *(0.5 pts)*

</ExamStatement>

**Solución.**

### a) Caso A, HTTP no persistente (conexiones TCP secuenciales) (1 pt)

- DNS: $\text{RTT}_1 + \text{RTT}_2$.
- HTML base: handshake ($\text{RTT}_s$) + GET ($\text{RTT}_s$) = $2\,\text{RTT}_s$.
- Cada imagen, con conexión nueva: $2\,\text{RTT}_s + S/R$.

$$T_A = (\text{RTT}_1 + \text{RTT}_2) + 2\,\text{RTT}_s + 3\left(2\,\text{RTT}_s + \frac{S}{R}\right) = \boxed{\text{RTT}_1 + \text{RTT}_2 + 8\,\text{RTT}_s + \frac{3S}{R}}$$

### b) Caso B, HTTP persistente sin pipelining (0,5 pt)

La conexión se abre una sola vez; cada imagen cuesta $\text{RTT}_s + S/R$.

$$T_B = (\text{RTT}_1 + \text{RTT}_2) + 2\,\text{RTT}_s + 3\left(\text{RTT}_s + \frac{S}{R}\right) = \boxed{\text{RTT}_1 + \text{RTT}_2 + 5\,\text{RTT}_s + \frac{3S}{R}}$$

### c) Cálculo numérico del caso B (0,5 pt)

$\text{RTT}_1 = 50$ ms, $\text{RTT}_2 = 70$ ms, $\text{RTT}_s = 100$ ms, $S = 2$ Mbits, $R = 10$ Mbps.

$$\frac{S}{R} = \frac{2\times10^6}{10\times10^6} = 0{,}2\text{ s} \qquad T_B = 0{,}120 + 5(0{,}100) + 3(0{,}2) = 0{,}120 + 0{,}500 + 0{,}600 = \boxed{1{,}220\text{ s}}$$

(Para el caso A con los mismos datos: $0{,}120 + 0{,}800 + 0{,}600 = 1{,}520$ s.)

## Pregunta 2: Protocolos RDT (4,5 puntos)

<ExamStatement>

Considere una transferencia de datos confiable (RDT) basada en el modelo 2.0 pero que incorpora un *timeout* para gestionar la pérdida de paquetes.

a) ¿Qué pasaría si el protocolo solo pudiera enviar mensajes **ACK**? Describa cómo funcionaría y cuáles serían sus desventajas. *(1 pt)*

b) ¿Qué pasaría si el protocolo solo pudiera enviar mensajes **NACK**? Describa cómo funcionaría y cuáles serían sus desventajas. *(1 pt)*

c) ¿Cómo gestionaría el envío de los paquetes en un sistema **NACK-only**? Plantee una propuesta de diseño para asegurar la confiabilidad del último paquete. *(0.5 pts)*

d) Considere un sistema que envía mensajes de manera **poco frecuente**. ¿Sería el protocolo NAK preferible frente al ACK? Justifique. *(1 pt)*

e) Considere un sistema con **alto volumen de datos** y un canal con **muy pocas pérdidas**. ¿Sería el protocolo NAK preferible frente al ACK? Justifique. *(1 pt)*

</ExamStatement>

**Solución.**

**a) Solo mensajes ACK (1 pt).** El receptor confirma cada paquete recibido bien; si el emisor no recibe el ACK (paquete perdido o corrupto) no avanza y, al vencer el temporizador, retransmite. *Desventaja*: no hay aviso temprano; toda falla se detecta solo por timeout, que debe ser lo bastante largo para no retransmitir de más. Cada paquete genera un mensaje de retorno.

**b) Solo mensajes NAK (1 pt).** El receptor calla mientras todo llega bien y envía un NAK cuando detecta un paquete corrupto o un hueco en la secuencia (para lo cual necesita **números de secuencia**). *Desventajas*: el emisor nunca recibe confirmación positiva, y una pérdida solo se detecta cuando llega un paquete posterior; el NAK mismo puede perderse.

**c) Último paquete en NAK-only (0,5 pt).** Si se pierde el último paquete, no llega ninguno posterior que revele el hueco y el receptor nunca envía NAK. Propuesta: que el emisor arme un temporizador tras el último paquete y lo marque como final; el receptor responde con una confirmación (ACK) solo a ese último paquete, y el emisor retransmite si no la recibe.

**d) Emisor que envía con poca frecuencia (1 pt).** *No* conviene NAK: un hueco solo se detecta cuando llega el siguiente paquete, y si pasa mucho tiempo entre envíos, la pérdida queda sin corregir durante ese lapso. Con ACK y timeout el emisor retransmite poco después de la pérdida.

**e) Alto volumen de datos y canal con pocas pérdidas (1 pt).** *Sí* conviene NAK: casi todos los paquetes llegan bien, así que con NAK el receptor casi no envía mensajes de retorno (con ACK habría uno por paquete). Como siempre hay tráfico, el siguiente paquete revela rápido cualquier hueco.

## Pregunta 3: Distribución de contenidos, C/S frente a P2P (3,5 puntos)

<ExamStatement>

Una universidad desea distribuir una imagen de disco de un laboratorio virtual de $F = 20$ GB a un grupo de $N = 150$ usuarios. El servidor central tiene una capacidad de subida $u_s = 40$ Mbps. Cada usuario tiene una capacidad de descarga $d_i = 12$ Mbps y una capacidad de subida $u_i = 3$ Mbps. (Considere 1 GB = 8000 Mb).

a) Calcule el tiempo mínimo de distribución ($D_{cs}$) necesario para que todos los usuarios obtengan el archivo bajo el modelo **Cliente-Servidor**. *(1 pt)*

b) Identifique cuál es el **factor limitante** (cuello de botella) en el modelo Cliente-Servidor para este escenario. *(0.5 pt)*

c) Calcule el tiempo mínimo de distribución ($D_{p2p}$) asumiendo que los usuarios colaboran entre sí (**P2P**) para redistribuir las piezas del archivo. *(1 pt)*

d) Si el número de usuarios aumenta a $N = 1000$, explique por qué el modelo P2P se considera "auto-escalable" comparado con el modelo Cliente-Servidor. *(1 pt)*

</ExamStatement>

**Solución.**

$F = 20$ GB $= 160\,000$ Mb (con 1 GB $= 8000$ Mb), $N = 150$, $u_s = 40$ Mbps, $d_i = 12$ Mbps ($d_{\min} = 12$), $u_i = 3$ Mbps.

**a) Cliente-servidor (1 pt).**

$$D_{cs} = \max\left(\frac{NF}{u_s},\ \frac{F}{d_{\min}}\right) = \max\left(\frac{150\cdot160\,000}{40},\ \frac{160\,000}{12}\right) = \max(600\,000\text{ s},\ 13\,333\text{ s}) = \boxed{600\,000\text{ s}}$$

(166,7 horas, casi 7 días).

**b) Cuello de botella (0,5 pt).** La **capacidad de subida del servidor** $u_s = 40$ Mbps: debe enviar $N$ copias completas.

**c) P2P (1 pt).**

$$D_{P2P} = \max\left(\frac{F}{u_s},\ \frac{F}{d_{\min}},\ \frac{NF}{u_s + \sum u_i}\right) = \max\left(4000,\ 13\,333,\ \frac{24\,000\,000}{40 + 450}\right)\text{ s}$$

$$D_{P2P} = \max(4000,\ 13\,333,\ 48\,980)\text{ s} = \boxed{\approx 48\,980\text{ s}}\quad(\approx 13{,}6\text{ h})$$

**d) $N = 1000$ (1 pt).**

$$D_{cs} = \frac{1000\cdot160\,000}{40} = 4\,000\,000\text{ s} \qquad D_{P2P} = \frac{1000\cdot160\,000}{40 + 3000} \approx 52\,632\text{ s}$$

Con $N$ de 150 a 1000, C/S crece **linealmente** con $N$ (de 6,9 a 46 días) mientras P2P apenas pasa de 13,6 h a 14,6 h: cada peer nuevo aporta su capacidad de subida $u_i$ al denominador, de modo que la capacidad de servicio crece con la demanda. Por eso P2P es **auto-escalable**.

## Pregunta 4: HTTP (1,5 puntos)

<ExamStatement>

Un navegador realiza la siguiente petición HTTP:

```text
GET /index.html HTTP/1.1
Host: www.somosciclo262.com
If-Modified-Since: Thu, 07 May 2026 10:15:00 GMT-5
```

a) ¿Cuál es la finalidad del encabezado If-Modified-Since en esta petición? *(0.5 pt)*

b) ¿Qué responderá el servidor si el recurso no ha sido modificado desde la fecha indicada? *(0.5 pt)*

c) ¿Qué ventajas en términos de ancho de banda y rendimiento ofrece este comportamiento condicional? *(0.5 pt)*

</ExamStatement>

**Solución.**


**a)** Es un **GET condicional**: el navegador pide `/index.html` solo si cambió después de esa fecha (la de su copia guardada).

**b)** Si no cambió, el servidor responde **`304 Not Modified`** sin cuerpo; el navegador usa su copia.

**c)** Ahorra ancho de banda (solo viaja la cabecera, no el objeto) y tiempo de respuesta (no se transmite el objeto, $L/R$).

## Pregunta 5: Caché DNS (1,5 puntos)

<ExamStatement>

Supongamos que puedes acceder y ejecutar comandos sobre las cachés de los servidores DNS locales de tu departamento. ¿Puedes proponer una forma de determinar aproximadamente cuáles son los servidores web (externos a tu departamento) más populares entre los usuarios de tu departamento? Explica tu respuesta.

</ExamStatement>

**Solución.**

Se puede **inspeccionar la caché** del DNS local: un servidor web externo cuyo nombre aparece en la caché fue consultado hace menos que su TTL. Se prueba con una lista de sitios candidatos y se repite el volcado a lo largo del tiempo: los nombres que **reaparecen** (con TTL renovado) cada vez que expiran son pedidos con frecuencia por varios usuarios del departamento. Es una estimación aproximada, porque la caché solo dice que alguien lo pidió, no cuántas veces.

| 4 | 4440 | 568 | no |

Solo el primer fragmento lleva la cabecera UDP (puertos). El destino reensambla los 4 fragmentos antes de entregar a UDP.

**c) PC-PT a Printer-PT (0,5 pt).** **No** hay fase de sincronización: UDP es **sin conexión** (no hay handshake); el emisor envía el datagrama directamente.

**d) Puerto 9999 cerrado (1 pt).** Lo notifica **ICMP**; en Wireshark se observa un mensaje ICMP *Destination unreachable (Port unreachable)* dirigido al origen del datagrama (Smartphone).

**e) Voz UDP interrumpida (0,5 pt).** **No**: FIN/RST son de TCP. UDP no mantiene estado de conexión, así que la capa de transporte del emisor no detecta la interrupción; si hace falta saberlo, lo debe detectar la aplicación.

**f) `ncat` UDP de Laptop (V2) a 192.168.101.20 (0,5 pt).** **No** es posible por Internet: 192.168.101.20 es una dirección **privada** de la red local de la Vivienda 1 (igual que 10.0.10.x en la Vivienda 2), que no se enruta en Internet. Solo sería alcanzable desde dentro de esa LAN.

**b) ¿Por qué el checksum de UDP difiere del de IP? (0,5 pt)** Son checksums distintos sobre datos distintos: el de IP cubre solo la **cabecera IP**; el de UDP cubre la **pseudocabecera** (IP origen/destino, protocolo, longitud), la cabecera UDP y los **datos**. Además, el de UDP se calcula sobre el datagrama completo, no por fragmento.

**c) ¿Por qué "unverified"? (0,5 pt)** Wireshark no lo pudo validar: la captura se hizo en el propio emisor (10.0.2.15) y el sistema operativo delega el cálculo del checksum a la tarjeta de red (*checksum offloading*), así que el valor que se ve aún no es el definitivo.

**d) ¿Hubo fragmentación? Offset del No. 30 (0,5 pt).** **Sí**: los frames 28 y 29 son fragmentos de un mismo datagrama (ID d0fb, "Reassembled in #30"). El datagrama UDP mide 4104 bytes y cada fragmento lleva 1480 bytes de carga, de modo que el frame 30 es el último fragmento:

$$\text{offset} = 2 \times 1480 = \boxed{2960\text{ bytes}}$$

(en la cabecera IP del frame 30, el campo vale 0x0172 = 370 unidades de 8 bytes = 2960 bytes; su carga son los $4104 - 2960 = 1144$ bytes restantes, que con 20 de cabecera IP y 14 de Ethernet dan los 1178 bytes del frame).

**e) MTU (0,5 pt).** **1500 bytes**: los fragmentos de 1514 bytes en el cable son 1500 de IP más 14 de la cabecera Ethernet.

**f) ¿Por qué "Malformed Packet" en el segundo frame? (1 pt)** El puerto de destino es **53**, así que Wireshark decodifica la carga como un mensaje **DNS**. La carga es una repetición de bytes 0x61 ("aaaa…"): la identificación vale 0x6161, el campo de flags 0x6161 (el código de operación sale como 12, "Unknown operation") y los contadores de preguntas y respuestas también 0x6161, valores imposibles para el mensaje que sigue. El mensaje no cumple el formato DNS, de ahí *Malformed Packet*. El primer mensaje (puerto 31337) no tiene un protocolo asociado y se muestra como datos.
